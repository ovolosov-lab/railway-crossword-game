# Развертывание «Железной дороги»

Это руководство описывает первое развертывание приложения из публичного GitHub-репозитория, первоначальное создание схемы и справочных данных через Alembic, а также подключение PostgreSQL. Пример Amvera основан на ее официальной документации; названия экранов и доступность функций у облачных платформ могут меняться.

## 1. Как устроено приложение

- Контекст сборки Docker — корень репозитория. [Dockerfile](../Dockerfile) устанавливает зависимости из `backend/requirements.txt`, копирует backend и frontend в образ и запускает Uvicorn на `0.0.0.0:8000`.
- Рабочий каталог контейнера — `/app/backend`. Команды Alembic выполняются именно из него; локально — из каталога `backend`.
- Приложение использует PostgreSQL через SQLAlchemy с асинхронным драйвером `asyncpg`. Оно принимает либо `DATABASE_URL`, либо комплект `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`. Если заданы оба способа, приоритет у `DATABASE_URL`. Источник истины — [настройки приложения](../backend/app/config.py).
- При запуске приложение проверяет соединение с БД и создает игровой раунд, но **не применяет миграции**. Миграции нужно выполнить отдельной командой до запуска новой версии приложения.
- MVP рассчитан на **один процесс приложения, один Uvicorn worker и одну реплику**. Раунд, таймеры и состояние игроков хранятся в памяти. Перезапуск сбрасывает активный раунд и его прогресс; несколько worker-ов/реплик не обеспечивают общее игровое состояние. Подробности — в [ADR 0002](./adr/0002-important-aspects-of-the-program-functioning.md).

## 2. Выбор способа размещения PostgreSQL

### Вариант A — отдельная управляемая БД (рекомендуемый для Amvera)

Создайте PostgreSQL как отдельный сервис/проект провайдера и подключите к нему приложение по внутренней сети. Так провайдер отдельно управляет жизненным циклом БД, хранилищем и резервными копиями. Создайте БД, пользователя приложения и пароль; сохраните выданные параметры подключения в менеджере секретов.

Для Amvera это штатный вариант: создается управляемый кластер PostgreSQL, а приложение обращается к нему по внутреннему доменному имени с суффиксом `-rw` для чтения и записи. Приложение и БД должны находиться в одном регионе. Используйте адрес, показанный в информации о кластере, а не угадывайте внутреннее DNS-имя. См. официальные разделы [PostgreSQL в Amvera](https://docs.amvera.ru/databases/postgreSQL.html) и [сетевое взаимодействие](https://docs.amvera.ru/applications/configuration/network.html).

Для Amvera создайте проект PostgreSQL, дождитесь состояния «PostgreSQL запущен», затем создайте отдельный проект-приложение. В переменные приложения внесите `DB_HOST` из информации о БД, `DB_PORT` (обычно 5432), `DB_NAME`, `DB_USER` и `DB_PASSWORD`. Публичный TCP-домен для приложения не нужен: используйте внутренний адрес. Подключение к PostgreSQL из Интернета настраивается отдельно и требует поддерживаемого клиентом SSL; не открывайте его без необходимости.

Другие облака могут выдавать `DATABASE_URL` вместо отдельных параметров. Уточните у провайдера адрес, порт, имя базы и требования TLS. Для приложения URL должен быть совместим с SQLAlchemy/`asyncpg`, например:

```text
postgresql+asyncpg://USER:PASSWORD@HOST:5432/railway
```

Это только шаблон, не готовая строка подключения. В URL специальные символы логина и пароля должны быть корректно percent-encoded. Если формат URL от провайдера отличается, проверьте его требования и формат драйвера; не заменяйте протокол вслепую. Альтернатива — передать параметры по отдельности, чтобы URL безопасно собрал SQLAlchemy.

### Вариант B — отдельный контейнер PostgreSQL

Используйте этот вариант только если выбранный облачный сервис поддерживает запуск нескольких связанных сервисов/контейнеров, сетевое имя сервиса и постоянный том. Например, в Compose приложение обращается к БД по `db:5432`; `localhost` внутри контейнера приложения указывает на само приложение, а не на контейнер PostgreSQL.

Схематический Compose-фрагмент:

```yaml
services:
  app:
    build:
      context: .
    environment:
      HOST: 0.0.0.0
      PORT: "8000"
      DB_HOST: db
      DB_PORT: "5432"
      DB_NAME: railway
      DB_USER: ${DB_USER}
      DB_PASSWORD: ${DB_PASSWORD}
      JWT_SECRET: ${JWT_SECRET}
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: railway
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  postgres_data:
```

Фрагмент иллюстрирует Compose-подобную схему и не является конфигурацией конкретного облака. Настройте публичную HTTP-маршрутизацию приложения согласно документации платформы. **Не публикуйте порт 5432 БД наружу.** Постоянный том обязателен: без него пересоздание контейнера может уничтожить данные. Проверьте, что условие `service_healthy` поддерживается вашей версией оркестратора. Файл [docker-compose.yml](../docker-compose.yml) в репозитории предназначен для локального запуска и служит более полным примером настроек.

**Не переносите этот вариант на Amvera как `docker-compose.yml`:** согласно [официальной документации Amvera по Docker](https://docs.amvera.ru/applications/configuration/docker.html), Docker Compose не поддерживается. Там следует создать отдельный управляемый PostgreSQL-сервис (вариант A).

## 3. Подготовка GitHub и облачного проекта

1. Опубликуйте проект в публичном GitHub-репозитории, убедившись, что в нем нет паролей, токенов, реальных `.env`-файлов, дампов БД и иных секретов. Оставьте в репозитории пример конфигурации без секретов.
2. Создайте PostgreSQL выбранным способом из предыдущего раздела. Для новой установки укажите имя БД `railway` либо другое согласованное имя и затем используйте его во всех настройках.
3. Создайте приложение в облаке и подключите публичный GitHub-репозиторий. Выберите ветку, которую будете разворачивать, и корень репозитория как контекст сборки: именно там находится Dockerfile, копирующий каталоги `backend` и `frontend`.
4. Публичный репозиторий обычно можно клонировать без доступа на запись. Однако настройка автоматической синхронизации/webhook может потребовать отдельный webhook secret или токен. Следуйте инструкции провайдера и не помещайте токен в репозиторий. Для Amvera см. [подключение GitHub и других Git-сервисов](https://docs.amvera.ru/applications/git/webhooks.html).
5. Проверьте, что платформа собирает образ из корневого [Dockerfile](../Dockerfile). Для Amvera Dockerfile достаточно; `amvera.yaml` нужен только для дополнительной настройки. Выберите Docker-окружение, если платформа требует указать тип сборки.

## 4. Переменные окружения и порт

Задавайте секреты в защищенной панели облака или его secret manager. Не добавляйте реальные значения в YAML, Dockerfile, GitHub Actions с открытым выводом, коммиты и логи. В Amvera секреты и обычные переменные задаются в разделе переменных; изменения требуют перезапуска контейнера. См. [переменные и секреты Amvera](https://docs.amvera.ru/applications/configuration/variables.html).

Обязательные настройки:

| Переменная | Назначение |
|---|---|
| `JWT_SECRET` | Секрет подписи JWT; не менее 32 байт UTF-8. Создайте случайное значение криптографическим генератором, например `python -c "import secrets; print(secrets.token_urlsafe(48))"`, и добавьте непосредственно в secret manager. Не используйте приведенную команду с фиктивным секретом как значение по умолчанию. |
| `DATABASE_URL` **или** все пять `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME` | Подключение к PostgreSQL. Пароль — секрет; остальные параметры тоже задавайте в настройках среды, а не в коде. |
| `HOST` | Адрес прослушивания HTTP. Для контейнера должно быть `0.0.0.0`, иначе внешний маршрутизатор не сможет обратиться к приложению. |
| `PORT` | Порт приложения. Должен совпадать с портом, который платформа направляет на контейнер. В текущем Dockerfile — `8000`. |

Рекомендуемые параметры:

| Переменная | Значение/назначение |
|---|---|
| `APP_ENV` | Установите `production`. |
| `DEBUG` | `false`. |
| `APP_NAME` | Необязательное отображаемое имя; по умолчанию `Railway`. |
| `JWT_ALGORITHM` | Поддерживаемое значение `HS256`; менять его не требуется. |
| `ACCESS_TOKEN_EXPIRE_MINUTES`, `AUTH_COOKIE_NAME`, `CSRF_COOKIE_NAME`, `AUTH_COOKIE_SAMESITE` | Настройки авторизации и cookies; при отсутствии используются безопасные значения по умолчанию в [config.py](../backend/app/config.py). |
| `GAME_DURATION_HOURS`, `CHECK_INTERVAL`, `USER_GUESS_RATE_LIMIT`, `FRONTEND_SYNC_INTERVAL`, `HINT_FIRST_LETTER_COST`, `HINT_LAST_LETTER_COST` | Параметры игры. Если нет отдельной причины менять, оставьте defaults приложения. |

Не копируйте [.env.example](../.env.example) целиком как конфигурацию облака: это локальный пример с параметрами, часть которых уже не используется приложением или не является текущей настройкой. Актуальный перечень и значения по умолчанию находятся в `backend/app/config.py`.

Для Amvera добавьте в корневой `amvera.yaml` только настройку порта, если используете значения из Dockerfile:

```yaml
run:
  containerPort: 8000
  servicePort: 80
```

В защищенных переменных приложения также задайте `PORT=8000` и `HOST=0.0.0.0`, чтобы фактический порт Uvicorn совпадал с `containerPort`. Публичный HTTP/HTTPS-домен настраивается отдельно в панели платформы. В Amvera порт внутри контейнера задается через `run.containerPort`; см. [Docker-конфигурацию](https://docs.amvera.ru/applications/configuration/docker.html) и [сетевое взаимодействие](https://docs.amvera.ru/applications/configuration/network.html). Для других платформ проверьте, передается ли `PORT` автоматически, и направьте трафик на фактически прослушиваемый порт.

## 5. Первоначальное создание схемы и загрузка справочников

### Перед миграцией

- Убедитесь, что PostgreSQL создана, доступна приложению/задаче миграции и учетная запись имеет права создавать таблицы и индексы.
- Настройте для команды миграции **те же** `DATABASE_URL` либо `DB_*`, что и для приложения. Она должна подключаться к нужной базе, например `railway`, а не к системной базе PostgreSQL.
- Для managed DB запускайте команду в окружении, которое имеет доступ к внутреннему адресу БД (например, одноразовая задача/консоль платформы или временный миграционный контейнер в той же сети). Если используете локальный компьютер, для него должен быть явно настроен разрешенный и безопасный сетевой доступ к БД. Не открывайте PostgreSQL всем адресам ради миграции.
- Не выполняйте миграцию в рабочей БД, пока не проверили адрес, имя базы и окружение.

### Выполнение

Запустите один раз в среде с установленными зависимостями проекта и корректными переменными БД:

```shell
cd backend
alembic upgrade head
alembic current
```

В контейнере из текущего Dockerfile рабочий каталог уже `/app/backend`, поэтому команда выглядит так:

```shell
alembic upgrade head
alembic current
```

Для локальной Compose-конфигурации из корня репозитория можно использовать отдельный одноразовый контейнер миграции. Сначала подготовьте локальный `.env` для Compose и убедитесь, что он не попадет в Git:

```shell
docker compose up -d db
docker compose run --rm app alembic upgrade head
docker compose up -d app
```

В этом случае `DB_HOST=db` доступен контейнерам в Compose-сети. При запуске Alembic непосредственно на хостовом компьютере вместо этого укажите доступный с хоста адрес БД, например `localhost` и опубликованный локальный порт; имя `db` на хосте обычно не разрешается.

Облачный интерфейс может называть такой запуск «одноразовой задачей», «консолью», «командой контейнера» или предлагать выполнить команду в отдельном временном экземпляре. Используйте поддерживаемый платформой механизм, не заменяя постоянную команду запуска веб-приложения миграцией. Если одноразового запуска нет, подготовьте отдельный временный миграционный контейнер из того же исходного кода/образа и с теми же переменными БД; после успешной миграции удалите его. Не запускайте миграции одновременно из нескольких реплик.

### Что загружается

`alembic upgrade head` последовательно создает объекты схемы и применяет версии миграций из [backend/migrations](../backend/migrations):

- начальные записи городов, а затем каталог городов и маршрутов из JSON-файлов миграций;
- слова и определения из нумерованных CSV в `backend/migrations/words`.

Ревизия загрузки слов требует пустую таблицу `dictionary_words`. Поэтому первоначальную установку выполняйте на новой/пустой базе и не загружайте слова вручную до миграции. Справочные файлы, уже использованные примененной миграцией, считайте неизменяемыми; обновления каталога вносите новой миграцией, а не редактированием старых файлов.

Не запускайте миграции автоматически при каждом старте веб-приложения: это усложняет откат, может создавать гонки при нескольких экземплярах и смешивает обслуживание схемы с запуском сервиса. Текущая конфигурация этого и не делает.

## 6. Проверка после развертывания

1. В выводе команды миграции проверьте успешное завершение, затем убедитесь, что `alembic current` показывает последнюю примененную ревизию и `alembic heads` — ожидаемую head-ревизию.
2. В подключенной к той же БД SQL-консоли проверьте, что справочники заполнены:

   ```sql
   SELECT
       (SELECT count(*) FROM cities) AS cities,
       (SELECT count(*) FROM routes) AS routes,
       (SELECT count(*) FROM dictionary_words) AS dictionary_words;
   ```

   Все три значения должны быть больше нуля. Не ориентируйтесь на заранее зафиксированное количество записей: оно зависит от актуальных миграционных каталогов.
3. Дождитесь состояния запущенного приложения и откройте `https://<ваш-домен>/health`. Ожидается HTTP 200 и `{"status":"ok"}`. Endpoint проверяет подключение к БД; HTTP 503 означает, что приложение не может выполнить запрос к PostgreSQL.
4. Откройте `/register/`, создайте временного пользователя, войдите и проверьте отображение игровой страницы/карты. Не используйте настоящий пароль или почту, если тестовые данные могут стать доступны операторам.
5. Если тестовый пользователь больше не нужен, удалите его штатным способом из приложения/БД после проверки. Не очищайте справочные таблицы и не сбрасывайте счетчики ради теста.

Если платформа поддерживает HTTP health probe, укажите путь `/health` и ожидаемый успешный статус. Не используйте проверку только порта как замену этой проверке: процесс может слушать порт, но не иметь соединения с БД.

## 7. Последующие обновления

1. Подготовьте и проверьте изменение локально, закоммитьте его и отправьте в выбранную GitHub-ветку.
2. До выпуска новой версии изучите новые миграции и сделайте резервную копию БД. При несовместимом изменении схемы составьте порядок переключения, который не оставит старую версию приложения работать с несовместимой БД.
3. Синхронизируйте платформу с GitHub (ручным pull или настроенным webhook) и соберите новый образ.
4. **До переключения приложения на код, требующий новой схемы**, один раз выполните `alembic upgrade head` отдельной командой/задачей, используя тот же адрес БД и релиз исходников.
5. Проверьте текущую ревизию и логи миграции, затем разверните новую версию приложения и повторите проверку `/health` и основных пользовательских сценариев.
6. Не запускайте команду миграций при старте каждого worker-а. В MVP сохраняйте одну реплику приложения и `--workers 1`.

Не считайте откат контейнера откатом схемы. Не применяйте `alembic downgrade` в рабочей базе без предварительной проверки конкретной downgrade-миграции и проверенной резервной копии. Например, seed-миграция слов при downgrade удаляет добавленные ею строки и не восстанавливает прежнее содержимое словаря.

## 8. Резервное копирование и восстановление

- В первую очередь используйте резервные копии управляемого PostgreSQL и изучите порядок восстановления у выбранного провайдера. Проверьте не только создание копии, но и восстановление в отдельную тестовую БД. После восстановления в новый кластер обновите секрет `DB_HOST`/`DATABASE_URL` приложения и проверьте `/health`.
- Для самостоятельного контейнера PostgreSQL обеспечьте бэкап самой БД и сохранность постоянного тома; снимок тома не всегда является согласованной резервной копией работающего PostgreSQL. Регулярно проверяйте восстановление дампа.
- Не храните дампы в публичном репозитории или общедоступном каталоге. Ограничивайте доступ и шифруйте копии в соответствии с возможностями платформы.
- На Amvera managed PostgreSQL имеет собственные возможности резервирования и восстановления; это отдельный механизм от бэкапов файлового `/data` приложения. См. [бэкапы PostgreSQL](https://docs.amvera.ru/databases/postgreSQL.html) и [хранилище/бэкапы приложений](https://docs.amvera.ru/applications/backups.html).
- Восстановление PostgreSQL возвращает сохраненные строки БД, но не активный раунд, таймер или текущий игровой прогресс: они существуют только в памяти единственного процесса. После перезапуска приложения создается новый раунд. Это ограничение MVP, а не ошибка восстановления БД.

## 9. Диагностика

| Симптом | Что проверить |
|---|---|
| Сборка не находит Dockerfile или не копирует frontend | Репозиторий подключен из корневого каталога; контекст сборки включает `Dockerfile`, `backend/` и `frontend/`. |
| Ошибка старта с `DATABASE_URL` или настройками БД | Все пять `DB_*` заданы, если не используется URL; адрес является внутренним DNS провайдера, порт и имя базы правильные; пароль/спецсимволы корректны; приложение и PostgreSQL находятся в совместимой сети/регионе. |
| `Connection refused`, timeout или DNS error | Дождитесь готовности БД, проверьте доступность по внутренней сети и имя сервиса; для контейнерной схемы используйте имя сервиса, а не `localhost`. |
| `/health` отвечает 503 | Посмотрите журналы приложения и PostgreSQL, доступность базы и учетные данные. Код запуска приложения при старте также проверяет соединение с БД. |
| Ошибка настройки JWT при старте | `JWT_SECRET` присутствует и содержит минимум 32 байта UTF-8; значение добавлено как секрет, а не оставлено примером. |
| Платформа показывает 502/503 при работающем процессе | Проверьте, что Uvicorn слушает `0.0.0.0`, `PORT` совпадает с `run.containerPort`/настройкой маршрутизатора и приложение действительно запущено. |
| Таблицы/справочники отсутствуют | Отдельно выполните `alembic current`, `alembic heads` и `alembic upgrade head` с правильными параметрами БД. Запуск приложения сам миграции не применяет. |
| Данные PostgreSQL пропали после пересоздания контейнера | Проверьте наличие постоянного тома и его правильное монтирование в каталог данных PostgreSQL. Образ контейнера без persistent storage не является постоянным хранилищем. |
| После деплоя изменился раунд или пропал прогресс | Это ожидаемое ограничение текущего MVP: перезапуск процесса сбрасывает игровое состояние в памяти. Проверьте, что случайно не запущено больше одной реплики. |

Читайте журналы сборки для ошибок Dockerfile/зависимостей и журналы приложения для ошибок запуска и подключений. В Amvera история журналов доступна во вкладках логов проекта; см. [сборку](https://docs.amvera.ru/applications/build.html) и [запуск](https://docs.amvera.ru/applications/run.html).
