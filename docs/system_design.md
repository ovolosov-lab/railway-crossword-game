# System Design: Веб-игра "Построй железную дорогу" (Кроссворд)

## 1. Общее описание
Многопользовательская игра, где игроки угадывают слова (кроссворды), расположенные на путях между городами Европы на интерактивной карте. Угаданное слово "строит" участок рельсов. Цель каждого игрока - проложить путь (железную дорогу) между двумя городами, назначенными каждому вошедшему в игру игроку случайным образом.

**Статус реализации:** код реализует индивидуальные сессии игроков по [ADR 0007](./adr/0007-continuous-game-player-sessions.md), API-контракту [ADR 0009](./adr/0009-game-api-contract.md) и [диаграмме состояний](./adr/0008-state-transition-diagram-user.md). Для текущей версии используйте [руководство развёртывания на Ubuntu VPS](./deployment.md). Прежний MVP с общим раундом и in-memory игровым состоянием описан отдельно в [архивном руководстве](./deployment_mvp.md); его инструкции не применяются к текущей версии.

## 2. Стек технологий
- **Backend:** Python 3.11+, FastAPI (асинхронный), Uvicorn
- **Database & ORM:** PostgreSQL, SQLAlchemy 2.0 (async), Alembic для миграций; Redis для временного игрового состояния целевой версии
- **Frontend:** Vanilla HTML5, CSS3 (Tailwind по желанию), JavaScript (Async/Fetch, Leaflet.js или SVG для карты)
- **AI Integration:** OpenAI API протокол (генерация описаний слов через LLM)
- **Auth:** JWT-токены (хранение в HttpOnly Cookies)
- **DevOps:** Docker, Docker Compose (`app`, `db`, `redis` и одноразовый `game-bootstrap`; Redis пока используется только для поколения и fencing)
- **Logging:** Loguru

## 3. Сущности и База данных

Долговечные данные: **User**, **City**, **Route** (участок сети), **DictionaryWord** и **GameResult**. Названия городов уникальны в каталоге и городов на карте - не больше 60; большинство записей — столицы, но это не обязательное ограничение. Участок может требовать несколько слов: `length_in_letters` в хранит максимальное количество помещающихся на участке букв, а не географическое расстояние. Слова назначаются маршрутам случайно из словаря; словарь не закреплён за участком.

Целевая игра непрерывна: общего раунда и таймера нет, победа одного игрока не завершает сессии других. У пользователя не более одной активной индивидуальной сессии; идентификатор сессии отличается от идентификатора пользователя. При сдаче очки текущей сессии сгорают, ранее сохранённый общий счёт не уменьшается.

Redis хранит активные сессии, их маршруты и промежуточные очки, использованные подсказки, а также слова и прогресс общих участков. Пока участок используется хотя бы одной активной сессией, его слова и их отгадывание общие; очки за слово получает первый угадавший. Пары городов уникальны среди активных игроков и освобождаются при завершении сессии. Слова располагаются вдоль участка без пересечений, с разделителями.

При открытии всех слов сессия переходит в состояние фиксации победы. Результат с уникальным ID сессии и начисление постоянных очков записываются в одной транзакции PostgreSQL; повтор не начисляет очки второй раз. Только после подтверждения победы Redis сохраняет состояние `won` и независимый снимок разгаданного кроссворда до новой игры или общего перезапуска. Другой игрок может открыть последнее слово и тем самым завершить эту сессию; он не получает за неё чужие очки.

Подсказки первой и последней букв сохраняются; повтор уже полученной подсказки бесплатен, а новую нельзя купить, если стоимость сделает счёт отрицательным. Подбор слов отдаёт предпочтение более длинным; правила fallback и пустого маршрута заданы в [ADR 0007](./adr/0007-continuous-game-player-sessions.md).

При полном развёртывании отдельный шаг создаёт новое игровое поколение: активные сессии и снимки побед не восстанавливаются, но подтверждённые в PostgreSQL результаты сохраняются. `python -m app.game_generation` выполняет bootstrap, а Compose запускает его через `game-bootstrap`. Worker при старте загружает текущее поколение; перезапуск приложения без bootstrap поколение не меняет. Redis хранит состояние игровой модели и fencing защищает операции устаревших workers. Текущий Compose настроен на одну app-реплику и один Uvicorn worker; руководство развёртывания не предписывает горизонтальное масштабирование.

Язык интерфейса, словаря и названий городов задаёт `LANGUAGE` (`ru` или `en`). Физические города хранятся в `physical_cities`, языковые записи с ключом `(id, lang)` — в `cities`, а маршруты ссылаются на физический ID. Интерфейсные строки локализуются по JSON-файлам в `locales`; миграции заполняют русские и английские записи словаря, не удаляя русские слова при добавлении английских. [ADR 0005](./adr/0005-game-api-contract.md) описывает контракт прежнего MVP, а [ADR 0009](./adr/0009-game-api-contract.md) — текущий контракт индивидуальных сессий.

## 4. Архитектура Проекта
Проект разделен на изолированные контексты бэкенда и фронтенда:
- `backend/app/` — асинхронный FastAPI код.
- `frontend/` — статика, шаблоны Jinja2 и сборщик Tailwind CSS.
```text
📂 Мой_Проект/
├── 📂 .agent_env/               # Инструкции для ИИ-агентов
├── 📂 docs/                     # Текстовая документация (System Design, Backlog)
├── 📂 logs/                     # Логи от Loguru (в .gitignore)
│
├── 📂 backend/                  # ВЕСЬ БЭКЕНД ЗДЕСЬ
│   ├── 📂 app/                  # Исходный код FastAPI (внутри каталоги auth, models, routes)
│   ├── 📄 main.py               # Точка входа FastAPI
│   └── 📄 requirements.txt      # Зависимости Python
│
└── 📂 frontend/                 # ВСЯ КЛИЕНТСКАЯ ЧАСТЬ ЗДЕСЬ
     ├── 📂 src/                 # Папка для Tailwind (входной CSS, JS модули)
     ├── 📂 static/              # Скомпилированный CSS, картинки, иконки городов
     │   ├── 📂 css/             # Сюда Tailwind будет собирать финальный файл
     │   ├── 📂 js/
     │   └── 📂 images/
     └── 📂 templates/           # HTML-шаблоны для FastAPI Jinja2
```
