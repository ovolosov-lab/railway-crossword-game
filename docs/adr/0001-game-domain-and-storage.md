# ADR 0001: Игровые сущности и хранение состояния

- **Статус:** внесены изменения в модель и созданы объекты Базы Данных (Superseded by [file](0002-important-aspects-of-the-program-functioning.md), [file](0003-important-aspects-of-the-program-functioning.md), [file](0003-game-frontend-functioning-aspects.md)), [file](0006-game-design-changes.md)
- **Дата:** 2026-10-20
- **Область:** модель PostgreSQL и состояние раунда игры

## Контекст

Раунд завершается по одному из двух событий: истекает ограничение в NN часов (интервал берется из конфигурации) либо первый игрок правильно отгадывает все слова своего маршрута. После завершения немедленно начинается следующий раунд. После авторизации игрока ему демонстируется блок со статистикой игры и кнопкой `Присоединться к игре` и если он присоединяется к текущему раунду (входит в игру) - за ним закрепляется пара городов (не имеет значения - какой из городов является началом, а какой - концом маршрута). Игрок самостоятельно прокладывает на карте непрерывный незакольцованный маршрут от одного города к другому из доступных маршрутов. Вдоль маршрута выстраивается кроссорд из следующих друг за другом слов. Слова выбираются случайно из общего словаря и закрепляются за маршрутом в течение раунда (но если какой-либо участок маршрута совпадает с выбранным ранее другим игроком участком маршрута, то закрепленное за выбранным раньше другим игроком участком маршрута слово становится загаданнм словом на этом участке и для новоно игрока: если участки совпали - слова тоже должны совпадать). Маршруты разных игроков могут частично совпадать. Но, за разными игроками не может быть закреплена одна и та же пара городов в текущем раунде. У разных игроков в одном раунде хотя бы один из городов пары должен различаться. 

Постоянные данные каталога и пользователей нужны между раундами. Текущее состояние игры временно, но хранение его только в памяти означает потерю раунда при перезапуске процесса и запрещает несколько независимых процессов приложения без общего хранилища состояния.

Подразумевается момент инициализации программы, когда один раз за весь жизненный цикл программы, в начале заполняются данными таблицы городов, возможных маршрутов (путей) между городами и полный, неизменяемый список слов с объяснениями от LLM, из которого для каждой игры будут выбираться случайным образом слова для кроссворда. 

## Решение

Для MVP использовать PostgreSQL для долговечных данных и in-memory объект для текущего раунда:

- В PostgreSQL хранить пользователей, города, участки железнодорожной сети, словарь и итог завершённого раунда.
- Не создавать таблицу `Game` для активного раунда и не сохранять назначенные маршрутам в раунде слова в таблицу `Word`.
- Держать идентификатор, время начала/окончания, участников, назначенные маршруты, выбранные слова и прогресс угадывания в одном объекте `ActiveGame` процесса приложения.
- При завершении раунда победой игрока в одной транзакции записать итог его игры в раунде в `GameResult`; только если запись нового результата успешна, начислить очки победителю. Уникальный `game_id` делает повторную обработку одного завершения идемпотентной.
- При timeout, когда нет ни одного победителя - НЕ записывать итог без победителя.
- Не удалять пользователей, города, маршруты и словарь каскадно: история результатов и целостность каталога должны сохраниться.

Это решение рассчитано на один процесс приложения. При нескольких worker-процессах или репликах инстансы не разделяют память, поэтому выдавать им трафик нельзя без общего хранилища активной игры.

### Начальная загрузка справочников городов и маршрутов

Начальные данные таблиц `cities` и `routes` хранятся в `backend/migrations/cities.json` и `backend/migrations/routes.json` и загружаются отдельной Alembic data migration после создания таблиц. JSON городов содержит обязательные поля `id`, `name`, `country_code`, `top`, `left` и `is_capital`; координаты задаются в пикселях фиксированного холста. Маршруты ссылаются на ID городов и задают положительное `length_in_letters` - вместимость участка маршрута в максимальном кличестве `квадратиков` кроссворда с буквами (т.е. максимальное количество букв, которое можно разместиь на этом участке пути, оно рассчитывается, как евклидово расстояние в пикселях между соседними точками городов, деленное на 26, где 26 - ширина одного `квадратика` с буквой внутри).

Перед записью миграция проверяет уникальность ID и названий городов без учёта регистра, формат кода страны, числовые координаты, уникальность неупорядоченной пары городов, существование обоих городов для каждого маршрута и связность сети. Каталоги являются исходными справочными данными и при обновлении миграции заменяются из JSON в одной транзакции; явные ID городов требуют синхронизации PostgreSQL identity sequence. Downgrade удаляет сеть маршрутов и восстанавливает каталог городов предыдущей версии.

### Уточнения требований

- В каталоге MVP не ожидаются повторяющиеся названия городов; имя города уникально без учёта регистра. В наборе данных преимущественно будут столицы, но модель не ограничивает каталог только столицами. Городов на карте будет не более 100 и карта не обязана быть абсолютно точной — допускаются искажения береговой линии и расположения городов. Координаты `top` и `left` задают положение точки на фиксированном холсте карты размером 4000 × 3000 пикселей (`top` — расстояние от верхнего края, `left` — от левого). Карта не масштабируется под разрешение экрана целиком: пользователь перемещается по ней прокруткой или перетаскиванием внутри видимой области. Координаты хранятся в единицах холста; модель и БД не накладывают диапазонное ограничение 0–1000. Проверка соответствия холсту относится к данным/логике карты, а не к ограничению схемы хранения. Для расчёта вместимости участка одна буква занимает 6 пикселей длины холста; например, при длине участка 163 пикселя помещается 27 ячеек, из которых 2 резервируются под отступы, то есть `length_in_letters` равен 27.
- Участки пути, которыми связаны два города, будут только между некоторыми городами (на граф должен быть связным - из любого города A должен существовать состоящий из отдельных путей межу городами маршрут к любому другому городу B), эти пути задаются, так же как и сами города с их координатами, один раз при инициализации программы. 
- Длинный участок пути может требовать несколько слов, общее количество которых зависит от числа букв в каждом отдельном слове; слова не пересекаются, поэтому при отборе слов по длине и расчете их количества на участке пути между двумя городами используется заранее определенная величина: максимально количество букв помещающихся на участке, записанная в поле `length_in_letters` таблицы `routes` (от этой величины нужно вычесть от 2 до 5 для обеспечения отступов между словами).   
- В будущем общее состояние активного раунда планируется хранить в Redis. До его внедрения используется память одного процесса, с ограничениями, описанными ниже. 
- Данные в таблицы БД - в таблицу списка слов с описаниями в таблицу городов предполагается загружать в момент начальной инициализации программы перед первым запуском, один раз.
- Категории для слов и подсказка по категории не используются; актуальное решение и требования к удалению этого функционала описаны в [ADR 0006](./0006-game-design-changes.md).

## Долговечная схема

Все модели SQLAlchemy 2.0 наследуются от `app.database.Base`. Времена хранятся как `TIMESTAMP WITH TIME ZONE` в UTC. UUID генерируется приложением через `uuid.uuid4`; учётные данные и параметры игры поступают из `config.py`.

### `users`

| Поле | SQLAlchemy / PostgreSQL | Правила |
|---|---|---|
| `id` | `Uuid`, PK | UUID, генерируется приложением |
| `username` | `String(32)` | NOT NULL; уникален без учёта регистра |
| `email` | `String(254)` | NOT NULL; уникален без учёта регистра |
| `hashed_password` | `String(255)` | NOT NULL; только хэш passlib/bcrypt, никогда пароль |
| `score` | `Integer` | NOT NULL, default 0, CHECK `score >= 0` |
| `is_active` | `Boolean` | NOT NULL, default true |
| `created_at` | `DateTime(timezone=True)` | NOT NULL, UTC |
| `updated_at` | `DateTime(timezone=True)` | NOT NULL, UTC |

JWT не хранится в таблице. Отзыв токенов и история входов не входят в текущую задачу.

### `cities`

| Поле | SQLAlchemy / PostgreSQL | Правила |
|---|---|---|
| `id` | `Integer`, PK | identity |
| `name` | `String(120)` | NOT NULL |
| `country_code` | `String(2)` | NOT NULL, ISO 3166-1 alpha-2, хранить uppercase |
| `top` | `Numeric(6, 2)` | NOT NULL | координата в пикселях фиксированного холста от верхнего края |
| `left` | `Numeric(6, 2)` | NOT NULL | координата в пикселях фиксированного холста от левого края |
| `is_capital` | `Boolean` | NOT NULL, default false |

В рамках MVP название уникально в каталоге без учёта регистра: UNIQUE индекс по `lower(name)`. `country_code` остаётся атрибутом города, а не частью ключа уникальности. Поле `is_capital` позволяет отмечать столицы, не предполагая, что каталог будет состоять только из них.

### `routes`

Маршрут здесь означает постоянный участок карты между двумя городами, а не случайно назначенную игроку последовательность слов.

| Поле | SQLAlchemy / PostgreSQL | Правила |
|---|---|---|
| `id` | `Integer`, PK | identity |
| `source_city_id` | `ForeignKey(cities.id)` | NOT NULL, `ON DELETE RESTRICT` |
| `target_city_id` | `ForeignKey(cities.id)` | NOT NULL, `ON DELETE RESTRICT` |
| `length_in_letters` | `SmallInteger` | NOT NULL, CHECK `> 0`; максимально количество букв помещающихся на участке слов |

В версии MVP участки считаются неориентированными: пара городов не должна дублироваться в обратном порядке. Использовать уникальный функциональный индекс по `LEAST(source_city_id, target_city_id)` и `GREATEST(...)`, а также CHECK `source_city_id <> target_city_id`. Если игре понадобятся параллельные железнодорожные линии между теми же городами, заменить это ограничение на уникальность по отдельному `route_code`.

### `dictionary_words`

В БД это каталог возможных слов, а не слово, уже назначенное в активный кроссворд. Актуальная схема без категории определена в [ADR 0006](./0006-game-design-changes.md).

| Поле | SQLAlchemy / PostgreSQL | Правила |
|---|---|---|
| `id` | `Integer`, PK | identity |
| `word_text` | `String(100)` | NOT NULL, отображаемая форма: существительные в нормализованной форме  |
| `definition` | `Text` | NOT NULL; описание, показываемое игроку |
| `language_code` | `String(5)` | NOT NULL, BCP 47 language tag |
| `letter_count` | `SmallInteger` | NOT NULL, CHECK `> 0`; число букв после нормализации |
| `is_active` | `Boolean` | NOT NULL, default true |
| `created_at` | `DateTime(timezone=True)` | NOT NULL, UTC |


### `game_results`

Это небольшая неизменяемая запись о завершении, а не полная запись активной игры. Создается при завершении раунда игры, если есть победитель

| Поле | SQLAlchemy / PostgreSQL | Правила |
|---|---|---|
| `game_id` | `Uuid`, PK | UUID; одновременно ключ идемпотентности 
| `winner_user_id` | `ForeignKey(users.id)` | NOT NULL; `ON DELETE RESTRICT` 
| `started_at` | `DateTime(timezone=True)` | NOT NULL, UTC |
| `finished_at` | `DateTime(timezone=True)` | NOT NULL, UTC, CHECK `>= started_at` 
| `score_awarded` | `Integer` | NOT NULL, CHECK `>= 0`

Начисление очков и вставка результата выполняются одной транзакцией.

## Связи ORM

- `User.game_results` — one-to-many к `GameResult`; у результата `GameResult.winner` — many-to-one к `User`.
- `City.outgoing_routes` и `City.incoming_routes` — два one-to-many отношения к `Route`, с явным `foreign_keys` для соответствующего endpoint.
- `Route.source_city` и `Route.target_city` — два many-to-one отношения к `City`.
- `GameResult` не ссылается на строку активной игры: её нет в долговечной схеме.

Именовать foreign key constraints явно, например `fk_routes_source_city_id_cities`, чтобы миграции были предсказуемы.

## Индексы

| Таблица | Индекс | Назначение |
|---|---|---|
| `users` | UNIQUE `lower(username)` | Регистрация и поиск имени без учёта регистра |
| `users` | UNIQUE `lower(email)` | Уникальность и поиск email без учёта регистра |
| `users` | `(score DESC, id)` | Таблица лидеров со стабильным порядком при равном счёте |

| `routes` | UNIQUE `(LEAST(source_city_id,target_city_id), GREATEST(...))` | Поиск участка и запрет обратного дубликата |
| `routes` | `(source_city_id)` и `(target_city_id)` | Поиск всех смежных участков из каждого endpoint; PostgreSQL не создаёт индексы на referencing FK автоматически |
| `dictionary_words` | UNIQUE `(language_code, word_text)` | Дедупликация и поиск слова |
| `dictionary_words` | `(language_code, letter_count) WHERE is_active` | Выбор подходящих активных слов по языку и длине |
| `game_results` | `(winner_user_id, finished_at DESC)` | История завершений конкретного игрока |
| `game_results` | `(finished_at DESC)` | Последние завершённые раунды |

Индекс не ускоряет чистую случайную сортировку `ORDER BY random()`. Для небольшого словаря она допустима как начальная реализация; при росте словаря измерить запрос и заменить выборку на выборку кандидатов по индексированным фильтрам с приложенческой случайной выборкой или иной проверенной стратегией.

## Модель активного раунда в памяти

`ActiveGame` и вложенные структуры являются моделями предметной области (например, dataclass), не SQLAlchemy ORM-моделями:

- `ActiveGame`: `game_id`, `started_at`, `expires_at`, состояние (`active`/`finished`), участники, необязательный победитель.
- `PlayerGameState`: `user_id`, назначенные `source_city_id`/`target_city_id`, список участков `route_ids` и упорядоченные размещения слов.
- Все слова для кросворда, выбранные в данном раунде для данного игрока - уникальны (нет повторяющихся).     
- `WordPlacement`: Слова размещаются только вдоль линии, соединяющей города (вдоль пути) и не пересекаются (одно заканчивается, затем, начинается другое), так что, у каждого слова имеется только одна координата размещения - `position_index`, кроме того, необходимы поля `dictionary_word_id`, `guessed_by_user_id` (nullable), `guessed_at` (nullable). Признак угаданности вычисляется как `guessed_by_user_id is not None`, чтобы не хранить два потенциально противоречивых значения. Угаданное слово сразу появляется на линии, соединяющей города.
- Количество слов на участке пути между двумя городами вычисяется исходя из значения в поле `length_in_letters` таблицы `Routes` и ограничения `оставить расстояние, равное длине от 2 до 5 клеток кроссворда под небольшие отступы межды словами`. Решение о том, какое слово для угадывания помещать на линию последним, должно приниматься, исходя из условий, что длина слова между минимальной и максимальной длиной из настроечных параметров и последнее слово не должно вылезать за пределы промежутка между городами. 
- Угадывание одного слова сразу открывает его клетки на экране. За каждое разгаданное слово кроссворда игрок получает призовые очки, зависящие от длины слова. Для победы игрок должен отгадать все назначенные ему записи слов. API скрывает неоткрытые буквы и не раскрывает `word_text` до угадывания, если только у другого игрока маршрут не совпадает частично с данным маршрутом: тогда слово, угаданное другим игроком, раскрывается для данного игрока, но очки за это слово ему не начисляются (только тому игроку, кто первый разгадал его). После угадывания всех слов на участке пути между двумя городами, вероятно, нужно будет изменять внешний вид соединяющей эти города линии (железная дорога).

Каждый раунд выбирает слова из `dictionary_words` без изменения каталога и без повторения одного слова в для одного пользователя. Это размещение слов существует только в состоянии раунда и осуществляется при входе данного пользователя в раунд игры. Пользователь авторизуется и сразу считается, что он вошел в игру - он видит у себя на экране карту с выбранными для него городами, например, Эдинбург и Мюнхен. Эти два города в текущем раунде уже не могут быть назначены оба одновременно другим игрокам. Не должно быть полных совпадений назначенных игрокам пар городов в одном раунде. Возможных маршрутов, соединяющих эти города, может быть на карте несколько. Поэтому, только что вошедшему в раунд игры новому игроку нужно дать возможность выбрать (проложить для себя) валидный, соединяющий начальный и конечный города одной линией (и не закольцованный нигде) маршрут. Это нужно потому, что, чем больше отрезков пути между соседними городами включает маршрут, тем больше очков получает данный игрок. У игрока должен быть выбор: проложить короткий маршрут и быстро выиграть или проложить более длинный маршрут - и заработать побольше очков. Каждый пользователь (игрок) видит клетки с разгаданными или неразгаданными словами только на своем маршруте. Но, маршруты двух разных игроков могут частично совпадать. Тогда: все слова на совпадающем участке пути у этих пользователей совпадают; 2) все разгаданные слова видны всем игрокам, у которых оказались эти же (совпадающие у разных игроков) участки пути. Но призовые очки за разгаданное слово получает только первым разгадавший это слово игрок. Проверка правильного ответа и переход в состояние победы должны быть атомарными внутри процесса: защищать обновление прогресса и завершение раунда одним `asyncio.Lock`, чтобы два одновременных запроса не назначили разных победителей.

Каждому игроку доступны две подсказки в текущем раунде игры: первая и последняя буквы слова. Стоимость каждой подсказки задаётся настройками. Подсказки запрашиваются у бэкенда; факт получения каждой подсказки хранится в состоянии игрока текущего раунда, чтобы повторный запрос не списывал очки повторно. Актуальные правила приведены в [ADR 0006](./0006-game-design-changes.md), контракт endpoint — в [ADR 0005](./0005-game-api-contract.md).

`length_in_letters` маршрута определяет количество записей слов, назначаемых этому участку; это максимальное число букв/клеток БЕЗ учета небольших отступов между клетками отдельных слов. 
Параметры длительности игры и начисления очков должны быть настройками приложения, не литералами в моделях.

Связи ORM со справочником городов в SQLAlchemy используют `passive_deletes=True`.

## Последствия и ограничения

- Перезапуск или авария процесса теряет активный раунд и его прогресс; при старте процесса создаётся новый раунд.
- Схема предполагает один worker и одну реплику. Нельзя безопасно масштабировать экземпляры без общего состояния и синхронизации.
- До подключения Redis активное состояние использовать только в одном процессе приложения. Перед запуском нескольких реплик перенести состояние раунда и координацию его обновлений в Redis; PostgreSQL остаётся источником долговечных результатов и каталога.
- Если продукту понадобится просмотр полной истории, достаточно расширить `GameResult` или добавить отдельные таблицы событий; записывать каждое временное слово в базу заранее не требуется.
- Каталог и `User.score` долговечны; завершённый результат хранится для аудита начисления очков, но активный кроссворд после окончания удаляется из памяти.

## План реализации

1. Создать ORM-модели каталога и пользователей с указанными ограничениями и связями.
2. Подключить модели к `Base.metadata` для Alembic autogenerate.
3. Подготовить миграцию таблиц, проверок и индексов.
4. Создать доменные модели для активного раунда отдельно от ORM и покрыть завершение/timeout конкурентными тестами.
5. До публичного многопроцессного запуска внедрить Redis как общее хранилище активного состояния и механизм координации.
