# ADR 0002: Важные аспекты функционирования игры

- **Статус:** описаны аспекты жизненного цикла MVP; детали реализации согласованы с Копайлот
- **Дата:** 2026-10-23
- **Область:** бэкенд, роутинг запросов фронтенда

## Контекст

Игра состоит из последовательных общих раундов. Раунд начинается независимо от того, авторизовался ли уже хотя бы один игрок. Он завершается либо когда игрок построил весь свой путь, либо по истечении заданного в конфигурации времени `GAME_DURATION_HOURS`.

В MVP приложение работает в одном процессе с одним worker. Активный раунд и прогресс игроков хранятся в памяти процесса. Закрытие или перезагрузка страницы не сбрасывает прогресс: после повторной авторизации фронтенд получает состояние текущего раунда с бэкенда. Перезапуск процесса, напротив, сбрасывает активный раунд и его прогресс. Это ограничение первой версии; сохранение активного состояния, Redis и запуск нескольких workers относятся к следующим этапам.

## Жизненный цикл раунда

1. При старте приложения сначала проверяется соединение с БД, после чего создаётся первый раунд.
2. Фоновая задача с интервалом `CHECK_INTERVAL` проверяет, истёк ли срок текущего раунда. Фактическое завершение по таймеру может произойти с задержкой до интервала проверки; для раундов длительностью 6, 12 или 24 часа задержка в несколько секунд допустима. Авторитетное время окончания задаётся бэкендом.
3. При победе раунд завершается сразу после обработки выигрышного действия, а результат записывается в `GameResult`. Завершение по таймауту означает, что до этого момента не было обработано выигрышное действие. В MVP такие раунды не записываются в `GameResult`: таблица хранит результаты состоявшихся побед.
4. Как только обнаружено завершение текущего раунда — по победе или истечению срока — без дополнительной заданной паузы начинается создание следующего раунда. Это означает немедленное начало процесса создания, а не мгновенную доступность уже запущенной игры для пользователя. Между раундами возможен короткий промежуток, пока новый раунд создаётся.

## Доступ к игре и поведение фронтенда

- Корневой HTML-маршрут `/` служит точкой входа: он проверяет HttpOnly JWT-cookie и наличие активного пользователя в БД. Неавторизованный пользователь, а также пользователь с отсутствующим, недействительным или истёкшим токеном перенаправляется на `/login/`; авторизованный пользователь перенаправляется на `/game/`.
- Проверка авторизации для `/` и защищённых HTML-страниц должна использовать общий механизм, который валидирует подпись и срок действия JWT, проверяет существование и активность пользователя. Ошибка БД не должна трактоваться как успешная или неуспешная авторизация и должна возвращаться как ошибка сервиса.
- Авторизованный фронтенд при обращении к игре получает текущее состояние раунда и время до его окончания. На основании этого времени фронтенд запускает отображаемый таймер обратного отсчёта; его можно завершать на 5–10 секунд раньше бэкендового срока, чтобы предупредить пользователя и начать переход к экрану ожидания. Клиентский таймер не завершает раунд на сервере и не заменяет проверку срока бэкендом.
- Порог `MM` минут применяется только при допуске нового игрока в текущий раунд. Если до конца раунда осталось не больше этого порога, новому игроку не назначается путь в текущем раунде; ему показывается сообщение, что новая игра вот-вот начнётся. Порог не блокирует запросы и игровые действия уже участвующих в раунде игроков.
- После окончания раунда фронтенд показывает соответствующее сообщение. Если следующий раунд ещё создаётся, пользователю сообщается, что новая игра вот-вот стартует. Фронтенд получает новый раунд при следующем запросе/обновлении состояния после его создания.
- Проверка HttpOnly JWT-cookie нужна для защищённых игровых страниц и API. Маршруты регистрации и авторизации, а также статические ресурсы доступны без авторизации. При отсутствии или недействительности токена защищённый HTML-маршрут перенаправляет пользователя на авторизацию; API возвращает ошибку в ожидаемом формате.

## Предлагаемые решения реализации

- Создавать начальный `ActiveGame` после проверки соединения с БД в `lifespan` приложения. Там же запускать фоновую задачу проверки истечения раунда и останавливать её при завершении приложения, как показано в [примере lifespan](./0002-game-main-lifespan-example.md).
- Проверку срока и переход к следующему раунду выполнять на стороне бэкенда. Обработчики игровых запросов также должны учитывать срок раунда, чтобы клиентский таймер не был источником истины.
- Настроить обработчики исключений в `main.py`, чтобы ошибки логировались, а клиент получал подходящий ответ: JSON для API и перенаправление с сообщением для HTML-сценария авторизации. Пример приведён в [документе об обработчиках исключений](./0002-game-Exception-handlers.md).

## Ограничения и отложенные решения

- В одном процессе состояние защищается от конкурентных изменений на уровне приложения. Несколько workers или реплик в этой версии не поддерживаются: у каждого процесса были бы отдельные раунды и таймеры.
- Активный раунд не переживает перезапуск сервера. Это ожидаемое ограничение MVP, а не гарантия восстановления.
- Точность окончания раунда ограничена интервалом фоновой проверки. Если в дальнейшем потребуется точное время завершения или работа нескольких workers, потребуется пересмотреть механизм хранения и координации состояния.

### Начальная загрузка справочника городов

Справочник `cities` загружается версионируемой Alembic data migration из `backend/migrations/cities.json` после создания таблицы. Миграция преобразует данные источника в формат модели `City`, задаёт коды стран и признак столицы, а после вставки явных идентификаторов синхронизирует identity sequence. Колонка `left` при использовании в SQL заключается в двойные кавычки, поскольку это ключевое слово PostgreSQL.

Изменения исходных данных справочника должны сопровождаться изменением миграции или новой миграцией, чтобы инициализация оставалась воспроизводимой.
