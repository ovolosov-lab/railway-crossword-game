# ADR 0010: Необязательные пересечения слов в кроссворде маршрута

**Статус:** согласован (2026-11-26); базовый алгоритм реализован в задаче 45, отдельный поиск поперечного слова в БД реализован в задаче 47 (2026-11-27). Поля и формат ответов API зафиксированы в [ADR 0009](./0009-game-api-contract.md).

## Контекст

В исходной одномерной версии генератор размещал слова только вдоль оси каждого участка маршрута. `offset_px` задавал продольное смещение слова от исходного города, а интерфейс рисовал все его клетки параллельно участку. Общие размещения создаются при публикации нового участка, хранятся вместе с состоянием участка в Redis и повторно используются участниками того же `round_id`.

Цель следующей версии — приблизить отображение кроссворда к привычной сетке, добавив возможность иногда размещать слова поперёк оси участка. Пересечения не являются целью генерации: допустимый и ожидаемый результат — кроссворд без поперечных слов.

## Решения

### 1. Пересечения необязательны

- Генератор не обязан создавать пересечение для каждого слова или участка.
- Если подходящих слов, букв или свободного места нет, слова размещаются вдоль участка по обычным правилам. Отсутствие пересечений не считается ошибкой и не требует повторной генерации.
- Поперечное слово остаётся самостоятельным игровым словом: его нужно отгадать, оно участвует в прогрессе участка и начислении очков на общих основаниях.
- Открытие одного из двух пересекающихся слов показывает общую букву в общей клетке. Это не раскрывает текст второго слова целиком; `word_text` неотгаданных слов остаётся закрытым.

### 2. Локальная система координат участка

Для каждого участка используются координаты его записи маршрута: от `source_city` к `target_city`, независимо от направления, в котором игрок проходит маршрут.

Пусть `u` — единичный вектор от исходного города к целевому, а `n` — вектор `u`, повёрнутый на `+90°`. Положительное направление поперечного размещения всегда задаётся через `n`; знак бокового смещения хранится в координате `y_offset_px`.

Для нового формата размещения предлагаются поля:

- `orientation`: `along` или `perpendicular`;
- `offset_px`: продольная координата центра первой клетки слова в локальной системе участка; у поперечного слова это `x` общей клетки пары;
- `y_offset_px`: знаковая координата центра первой клетки относительно оси участка; для слова вдоль пути равна `0`;
- `crossing_id` и `crossing_index` для слов, образующих пару: общий идентификатор пересечения и нулевой индекс общей буквы в конкретном слове.

Клетки слова `along` идут вдоль `u`; клетки слова `perpendicular` — вдоль `n`. Если `p` — шаг между центрами клеток, то для продольного слова `A` с первой клеткой в `offset_A_px` центр клетки с индексом `k` находится в точке `(offset_A_px + k*p, 0)`. Пусть общая буква находится в продольном слове на индексе `i_A`, а в поперечном слове `B` — на индексе `j_B`. Тогда координата пересечения по `x` равна `x_cross = offset_A_px + i_A*p`. Первая буква поперечного слова имеет координаты `(x_cross, y_offset_B_px)`, а клетка `B` с индексом `j` — `(x_cross, y_offset_B_px + j*p)`: у всех букв поперечного слова одинаковый `x`, меняется только `y`. Для общей клетки должно выполняться `y_offset_B_px + j_B*p = 0`. В терминах отдельных размещений `offset_B_px` поперечного слова равен `x_cross`; сервер может передать его явно или вычислить из продольного смещения и индекса пересечения. Индексы `i_A` и `j_B` различны и не должны подменяться одним общим индексом.

Координаты клетки и шаг `p` используют одну согласованную систему единиц исходной карты. Обновлённый контракт API в ADR 0009 задаёт в `offset_px` координату центра первой клетки; при переходе прежнее смещение начала слова преобразуется с учётом половины шага клетки. Backend и frontend переходят на новый контракт совместно. Перед развёртыванием все старые игровые состояния Redis сбрасываются, поэтому миграция старых координат Redis не выполняется.

Для пары сервер проверяет, что координаты клеток с индексами `crossing_index` совпадают, а буквы в этих клетках одинаковы. Индексы букв и идентификатор пары передаются во всех проекциях кроссворда, включая `/game/route/`, `/game/sync/` и снимок победы. Они описывают геометрию и не раскрывают ответ неотгаданного слова.

### 3. Правило поиска пары

Базовый пул и продольная раскладка создаются так же, как при генерации без пересечений. Все слова пула остаются `along`; новое поперечное слово выбирается отдельным запросом к `dictionary_words` и добавляется к кроссворду.

Слова пула остаются `along`. Первое и последнее слова продольного ряда не могут быть якорями, поскольку находятся у городов на концах участка. Каждое внутреннее слово рассматривается независимо как якорь; соседнее продольное слово для этого не требуется:

1. Для внутреннего слова-якоря проверяются буквы внутренних клеток слева направо.
2. Бэкенд выполняет отдельный запрос к `dictionary_words` за активными словами языка `LANGUAGE` длиной от 3 до 7 клеток. Слова, уже присутствующие в базовом пуле, на опубликованных участках маршрута или среди ранее выбранных поперечных кандидатов, исключаются после игровой нормализации.
3. Среди результатов запроса рассматриваются слова с такой же буквой во внутренней позиции. Выбирается первая буква якоря, для которой найдены кандидаты, проходящие геометрическую проверку. Если подходящих слов несколько, одно выбирается случайно; индекс общей буквы в каждом слове становится его `crossing_index`.
4. Кандидат из БД добавляется как `perpendicular` только если проходит проверку геометрии полного маршрута. Базовые слова и их продольные координаты при этом не меняются.
5. После проверки якоря поиск продолжается со следующего продольного слова. Каждое внутреннее слово-якорь может получить не более одного поперечного слова. Если подходящего слова в БД нет или кандидаты не проходят геометрическую проверку, этот якорь пропускается, а базовая раскладка остаётся без изменений.

Запрос получает кандидатов допустимой длины одним обращением к БД для каждого проверяемого якоря; проверка нормализованной уникальности, внутреннего совпадения и геометрии выполняется до случайного выбора. Минимум в три клетки нужен для внутренней буквы, верхняя граница поперечного кандидата равна семи клеткам. Длина продольного слова-якоря этим правилом не ограничивается.

### 4. Ограничения и защита концов участка

- Число пар — верхний предел, а не цель: не более трёх пар на длинном участке и не более одной на коротком. Для `n` продольных слов структурно доступно не более `max(0, n - 2)` якорей — все внутренние слова. Поэтому три пересечения возможны начиная с пяти продольных слов; при 2, 3, 4 и 5 словах структурный максимум равен соответственно 0, 1, 2 и 3. Коротким считается участок, для которого базовый продольный расклад не позволяет разместить три слова так, чтобы среднее слово содержало не менее трёх символов. На любом участке допустимо ноль пар.
- Все слова исходного продольного расклада, в том числе первое и последнее, остаются `along`; первое и последнее не могут быть якорями. Внутренние слова остаются в продольном ряду и независимо проверяются как якоря.
- При двух словах или меньшем количестве внутренних якорей нет. Три продольных слова дают один внутренний якорь, поэтому одно пересечение структурно возможно при наличии подходящего слова и свободной геометрии.
- Продольная длина и интервалы между словами расходуют ёмкость участка. Новое поперечное слово не вычитается из продольной ёмкости; вместо этого учитывается его поперечный габарит и занятые клетки.

#### Запрос слова-кандидата для пересечения

На каждый внутренний якорь выполняется один дополнительный запрос за кандидатами `perpendicular` длиной от 3 до 7 клеток; слова предварительного пула остаются продольными и не заменяются. Кандидат выбирается случайно среди неиспользованных слов с общей внутренней буквой и свободной геометрией. Базовые продольные слова сначала выбираются для полного маршрута, поэтому запросы поперечных кандидатов не уменьшают пул для заполнения других участков. Словарь не изменяется; выбранное слово становится частью общего состояния сегмента в Redis.

Поперечное слово — отдельное игровое слово: оно увеличивает число слов, которые предстоит отгадать, участвует в прогрессе и начислении очков на общих основаниях. Одно внутреннее слово-якорь образует не более одной пары; на одном участке выбираются разные поперечные слова.

### 5. Геометрический фильтр и занятое пространство

Косинус угла рассматривается как предварительный фильтр у концов участка. Угол определяется между лучом от общей вершины внутрь текущего участка и каждым лучом от этой вершины внутрь соседнего участка того же маршрута. Условие допуска — каждый такой угол строго больше `80°`; для единичных векторов это скалярное произведение меньше `cos(80°)` (примерно `0.174`). Если у конца нет соседнего участка маршрута, этот локальный фильтр там не ограничивает размещение.

Угловой фильтр сам по себе не доказывает отсутствие столкновений. Перед публикацией пары генератор должен проверять клетки поперечного слова относительно полного маршрута игрока, подтверждающего этот путь:

- осей всех участков этого маршрута, включая участки, уже опубликованные и повторно используемые из общего состояния;
- уже опубликованных клеток слов на этих участках.

Единственное допустимое пересечение с текущим участком — общая клетка выбранной пары. Если другая клетка поперечного слова попадает на ось другого участка маршрута или на занятую клетку, пара отклоняется. Неиспользуемые линии карты и участки из несовпадающих маршрутов других игроков не являются препятствием: интерфейс показывает игроку клетки своего маршрута; общий участок с тем же `route_id` использует уже опубликованное общее размещение.

Проверка при первой публикации учитывает весь маршрут её владельца. Позже другой игрок может повторно использовать общий участок с уже созданным поперечным словом, выбрав при этом иное продолжение маршрута. Возможное столкновение клеток общего участка с новым продолжением не меняет опубликованный общий кроссворд.

### 6. Общие сегменты и состояние игры

Размещение остаётся общим для `(round_id, route_id)`: первая публикация сегмента сохраняет выбранные слова, ориентации и координаты в Redis, а остальные участники того же раунда видят те же клетки и пересечения. Опубликованный сегмент не перестраивается при подключении новых игроков или повторном подтверждении маршрута. Новый раунд может получить отдельное размещение на том же физическом участке.

Геометрические поля должны сохраняться и проверяться вместе со словами в Redis, проекциях API и снимке победы. Решение не требует изменения PostgreSQL, пока размещения кроссворда остаются данными Redis. Перед развёртыванием новой схемы все старые игровые состояния Redis сбрасываются; перенос старых сессий и размещений не выполняется.

## Последствия

- Генератор и интерфейс должны перейти от одномерной модели слова к модели ориентированных клеток в локальной системе участка.
- Проверка ёмкости участка станет раздельной: продольное заполнение не учитывает длину поперечного кандидата, а геометрическая проверка учитывает его фактические клетки.
- Для каждого проверяемого внутреннего якоря потребуется один дополнительный запрос за поперечными кандидатами; исходный продольный пул и его раскладка остаются неизменными.
- Дополнительное поперечное слово увеличивает число слов, которые предстоит отгадать, но не меняет формулу очков за слово.
- Запрос поперечного слова выполняется только при первой генерации нового участка; результат сохраняется в общем состоянии Redis вместе с геометрией сегмента.
- Отгаданное слово может открыть одну общую букву в неотгаданной паре. Клиенту потребуется отрисовывать общую клетку один раз и брать её букву из уже отгаданного слова.
- Пересечения генерируются до публикации общего сегмента и затем остаются неизменными для участников этого раунда.

## Вне объёма этого решения

- Гарантированное наличие пересечений в каждом кроссворде или у каждого продольного слова.
- Глобальная оптимизация сетки, чтобы все слова образовывали классический прямоугольный кроссворд.
- Улучшение читаемости повёрнутого текста поперечных слов; на этом этапе фиксируется геометрия клеток и букв.
- Изменение правил начисления очков, подсказок, победы, `round_id` или совместного владения сегментом.

## Позднее продолжение маршрута: принятый компромисс

Если новый игрок повторно использует общий сегмент с уже опубликованным поперечным словом, но выбирает другое продолжение, возможное геометрическое столкновение с клетками этого продолжения не устраняется перестроением общего сегмента. Принято не отклонять из-за этого маршрут и не менять опубликованный общий кроссворд: редкое визуальное наложение допустимо для необязательной функции. Строгая гарантия отсутствия таких наложений потребовала бы отдельного решения, ограничивающего выбор маршрута или проверяющего размещение против всех потенциальных продолжений.

Если в процессе разработки или проверки обнаружатся другие коллизии либо потребуется пересмотреть принятые здесь ограничения, вопрос сначала обсуждается отдельно. Согласованные изменения оформляются дополнительным ADR 0012; ADR 0010 сохраняет зафиксированные для этой версии решения.
