# ADR 0005: Контракт игрового API

- **Статус:** согласованный
- **Дата:** 2026-10-28
- **Область:** HTTP API игровой страницы `game.html`
- **Связанные решения:** [ADR 0001 — домен игры](./0001-game-domain-and-storage.md), [ADR 0003 — функционирование игры](./0003-important-aspects-of-the-program-functioning.md), [ADR 0003 — фронтенд игры](./0003-game-frontend-functioning-aspects.md), [ADR 0004 — переходы состояний пользователя](./0004-state-transition-diagram-user.md)

## 1. Цель и принятые решения

Этот документ задаёт проект JSON API для реализации игрового цикла. Выбранные вместе с владельцем проекта решения:

1. Присоединение и подтверждение пути — два шага: `POST /game/join/` назначает города, `POST /game/route/` принимает выбранные рёбра и запускает игру участника.
2. Успешные запросы возвращают 2xx, ошибки используют подходящие HTTP-коды и JSON-ответ с машинным кодом ошибки. Ошибки не маскируются статусом `200`.
3. Промежуточный счёт игрока хранится только в памяти активного раунда. При победе итоговый счёт победителя добавляется к `users.score` и фиксируется в `game_results`. Если победителя нет, `GameResult` не создаётся и промежуточные очки участников не сохраняются.

Контракт согласован для реализации MVP. Решения раздела 8 считаются принятыми; параметры окружения и ограничения MVP должны реализовываться согласно указанным в документе правилам.

## 2. Общие правила

- Базовые пути ниже приведены без глобального `/api` префикса, чтобы сохранить адреса, уже перечисленные в ADR.
- Игровые страницы и endpoints требуют авторизации. Пользователь определяется только по JWT в HttpOnly cookie; клиент не передаёт `user_id` как источник идентичности.
- JSON-запросы используют `Content-Type: application/json`; ответы — `application/json`.
- Для межсайтовых cookie-запросов изменения состояния должны быть защищены CSRF-токеном. JWT не возвращается в JSON и не помещается в URL.
- Время передаётся в ISO 8601 UTC, например `2026-10-28T12:00:00Z`. `remaining_seconds` вычисляется сервером; значение таймера браузера не является основанием для приёма или отклонения игрового действия.
- Идентификаторы раунда (`round.id`) и игрового слова (`placement_id`) непрозрачны для клиента. `placement_id` не содержит текст ответа.
- В телах запросов, относящихся к раунду, его идентификатор передаётся плоским полем `round_id`. В ответах идентификатор входит в объект `round` под именем `id` (`round.id`).
- Ни один ответ API не раскрывает `word_text` до того, как соответствующее слово отгадано. Синхронизация может раскрыть уже угаданное слово на совпадающем участке маршрута.
- `route_ids` в запросе подтверждения передаются в порядке прохождения пути. Сервер повторно проверяет принадлежность рёбер каталогу, непрерывность, концы пути, отсутствие повторных рёбер и циклов.
- `state_version` — монотонно растущая версия состояния раунда. Клиент игнорирует ответ с версией ниже уже отображаемой, чтобы запоздавший polling не откатил интерфейс.
- Обработчики изменения состояния проверяют дедлайн раунда и берут общий lock до проверки и изменения состояния. Это относится как минимум к присоединению, подтверждению пути, угадыванию и подсказке.
- Повтор запроса не должен повторно назначать города, засчитывать одно слово или списывать стоимость уже использованной подсказки. Идемпотентность обеспечивается состоянием участника и записи слова/подсказки; если клиентский retry нельзя распознать по ресурсу, запрос дополнительно принимает `Idempotency-Key`.
- Победитель — игрок, чей запрос первым под lock зафиксировал последнее необходимое слово и завершил маршрут; остальные участники считаются проигравшими, даже если этот же ответ завершил и их маршрут. 

### Состояния в API

`round.status`:

- `active` — раунд принимает действия;
- `finished` — раунд уже завершён; причина находится в `finish_reason`;
- `being_created` — следующий раунд ещё создаётся или текущий недоступен.

`player.state`:

- `watching_stats` — пользователь не присоединился к текущему раунду;
- `selecting_route` — города назначены, путь ещё не подтверждён;
- `playing` — путь подтверждён, кроссворд создан;
- `won` — игрок победил в завершённом раунде, важное состояние на бэкенде, НО, на фронтенде игрок, фактически, не переходит в это состояние, он получает в ответе бэкенда это состояние игрока и оно является триггером для демонстрации игроку `Экрана победы`, но, фактически, в этот момент состояние игрока сразу меняется на `watching_stats` а не после демонстрации `Экрана победы`;
- `lost` — игрок участвовал, но раунд завершился без его победы - тоже, что и для состояния `won` - получается в ответе бэкенда и исрок переходит в состояние `watching_stats` а ему демонстрируется Ободряющее сообщение о проигрыше.

`round.finish_reason` для завершённого раунда: `winner` или `timeout`. Статус `closed_other_winner` из прежнего предложения выражается сочетанием `round.status=finished`, `finish_reason=winner`, `player.state=lost`. 

Время показа экранов результата — примерно 30 секунд; эта выдержка относится к UI и не задерживает создание следующего раунда и изменение статуса игрока не задерживается на время демонстрации.

## 3. Формат ошибок

Для ошибки возвращается объект:

```json
{
  "error": {
    "code": "route_not_connected",
    "message": "Выбранные участки не образуют непрерывный путь между назначенными городами.",
    "details": null
  }
}
```

Использовать HTTP-коды по смыслу:

| HTTP | Когда |
|---|---|
| `400` | Некорректный формат запроса, который нельзя разобрать как JSON |
| `401` | Нет действующей авторизации |
| `403` | Действие запрещено для текущего участника |
| `404` | Раунд или `placement_id` не найден/не принадлежит доступному состоянию игрока |
| `409` | Конфликт состояния: раунд завершён, игрок уже выбрал несовместимый путь, повторный запрос конфликтует с сохранённым выбором |
| `422` | JSON синтаксически корректен, но тело или query-параметры не прошли валидацию |
| `429` | Превышен лимит запросов, если он включён |
| `500` / `503` | Неожиданная ошибка приложения или временная недоступность сервиса |

Ошибки игровых состояний должны содержать стабильный `error.code` и при необходимости актуальные `round` и `player` projections, чтобы интерфейс мог перейти в правильное состояние. API-запрос авторизации возвращает `401` JSON, а не HTML redirect; redirect с flash-сообщением применяется при навигации браузера на защищённую HTML-страницу.

## 4. Endpoints

### `GET /game/stats/`

Возвращает состояние текущего раунда и публичную статистику победителей. Требует авторизации, но не присоединяет пользователя.

Пример:

```json
{
  "round": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "started_at": "2026-10-28T12:00:00Z",
    "expires_at": "2026-10-28T18:00:00Z",
    "remaining_seconds": 1250,
    "finish_reason": null,
    "state_version": 14
  },
  "player": {
    "state": "watching_stats"
  },
  "participant_count": 8,
  "leaderboard": [
    {"username": "player_one", "score": 1240}
  ]
}
```

Рейтинг строится по `users.score`; в него входят только зафиксированные победы. Не возвращать email, хэш пароля, JWT и другие приватные данные.

### `GET /game/routes/`

Возвращает карту доступных участков и персональную игровую проекцию. Endpoint нужен для отрисовки карты и восстановления страницы после перезагрузки. Если игрок уже участвует в активном раунде, вернуть `selecting_route` или `playing` вместе с его назначенными городами и данными маршрута; не создавать новое участие этим GET-запросом.

Основное содержимое:

```json
{
  "round": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "remaining_seconds": 1250,
    "state_version": 14
  },
  "player": {
    "state": "watching_stats",
    "source_city_id": null,
    "target_city_id": null,
    "route_ids": []
  },
  "cities": [
    {"id": 1, "name": "Лондон", "top": 1405, "left": 779}
  ],
  "routes": [
    {"id": 1, "source_city_id": 1, "target_city_id": 2, "length_in_letters": 14}
  ]
}
```

Координаты маршрутов на клиенте выводятся из координат городов и карты; они не заменяют серверную проверку пути.

### `POST /game/join/`

Назначает не участвующему в раунде пользователю пару городов и переводит его в `selecting_route`. Тело запроса пустое. Сервер атомарно проверяет, что раунд `active` и до конца больше 60 секунд.

- Если пользователь уже присоединился к этому раунду, вернуть его текущее состояние без повторного назначения.
- Не назначать ту же неориентированную пару городов, которая уже выдана другому игроку в этом раунде; хотя бы один город пары должен различаться с каждой ранее выданной парой.
- Если активного раунда нет либо до дедлайна осталось не более 60 секунд, вернуть HTTP `200` с актуальными `round`/`player`, `player.state=watching_stats` и `round.status=being_created` или `finished`; не создавать участника. Это допустимое состояние интерфейса, а не ошибка запроса.

Успешный ответ:

```json
{
  "round": {"id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10", "status": "active"},
  "player": {
    "state": "selecting_route",
    "source_city_id": 1,
    "target_city_id": 29,
    "route_ids": []
  }
}
```

При отсутствии доступной уникальной пары не выбирать занятые города молча: вернуть явную ошибку `409 city_pairs_exhausted` и возвратить игрока в состояние `watching_stats`.

### `POST /game/route/`

Подтверждает непрерывный путь и создаёт персональную проекцию кроссворда.

Запрос:

```json
{
  "round_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
  "route_ids": [1, 3, 5]
}
```

Сервер проверяет активность раунда, состояние игрока, непрерывность в указанном порядке, использование назначенных городов как двух концов, отсутствие циклов и повторов, а также наличие слов для формирования кроссворда (отдельные (не все сразу) участки, в связи со слишком маленьким расстоянием между точками-городами, могут остаться без слов - такое допускается; просто эти участки будут сразу помечены как пройденные). Проверка на клиенте служит только UX.

Для принятого пути сервер создаёт размещения на постоянных участках маршрутов. Если общий участок уже имеет слова в этом раунде, повторно использует их и общее состояние угаданности; иначе назначает слова из каталога. Угаданное слово открывается участникам с общим участком, но очки за его отгадывание начисляются только первому угадавшему.

`position_index` — нулевой индекс первой ячейки строки слова вдоль участка. Каждый символ `word_text`, в том числе пробелы и знаки пунктуации, занимает одну ячейку и учитывается в длине; между словами резервируется одна пустая ячейка. Суммарная длина символов и промежутков не превышает `length_in_letters`. Участок, на котором не помещается ни одного подходящего слова, остаётся пустым и считается пройденным; если пуст весь выбранный путь, сервер удаляет участие и освобождает пару городов, а затем возвращает `503 crossword_generation_failed`.

Успешный ответ содержит только публичное представление размещений:

```json
{
  "round": {"id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10", "status": "active"},
  "player": {"state": "playing", "route_ids": [1, 3, 5]},
  "crossword": [
    {
      "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
      "route_id": 1,
      "position_index": 0,
      "letter_count": 6,
      "definition": "Описание слова без его отгадки.",
      "is_guessed": false,
      "guessed_by_me": false,
      "hint_types_used": []
    }
  ],
  "state_version": 15
}
```

Не включать `word_text`, `normalized_word` или иной материал, из которого можно восстановить отгадку.

Повтор с тем же путём возвращает уже созданное состояние и те же `placement_id`. Если клиент не получил ответ на подтверждение из-за сетевой ошибки, он повторяет тот же `POST /game/route/` с прежними `round_id` и `route_ids`; повтор безопасно восстанавливает ответ. Попытка заменить подтверждённый путь — `409 route_already_confirmed`; изменение пути после начала разгадывания в этом MVP не поддерживается. После `503 crossword_generation_failed` клиент возвращает пользователя к статистике и предлагает присоединиться к раунду заново: прежнее участие уже удалено, пара городов освобождена.

### `POST /game/guess/`

Проверяет ответ участника и, если он правильный, атомарно отмечает общее слово угаданным.

Запрос:

```json
{
  "round_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
  "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
  "answer": "пример"
}
```

Ответ при правильной отгадке:

```json
{
  "round": {"id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10", "status": "active"},
  "player": {"state": "playing", "round_score": 60},
  "guess": {
    "result": "correct",
    "already_solved": false,
    "points_awarded": 60,
    "revealed_word": "ПРИМЕР"
  },
  "state_version": 16
}
```

Ответ при победе данного игрока:

```json
{
  "round": {"id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10", "status": "finished", "finish_reason": "winner"},
  "player": {"state": "won", "round_score": 460},
  "guess": {
    "result": "correct",
    "already_solved": false,
    "points_awarded": 90,
    "revealed_word": "ШРЕДИНГЕР"
  },
  "state_version": 17
}
```

`round.id` в ответе всегда должен быть равным `round_id` в запросе, т.е. соответствовать текущему раунду игрока, даже если на фронтенде этот раунд завершился к моменту прихода запроса от фронтенда (в таком случае `round_id` берется из инстанса PrevGame).

Если повторный `/game/guess/` поступил после завершения раунда, сервер до обычной проверки участия сверяет его `round_id` и идентификатор пользователя из JWT с `PrevGame.round_id` и `PrevGame.winner_user_id`. При совпадении сервер без изменения состояния и без повторной записи результата или начисления очков возвращает HTTP `200` с терминальным исходом победителя:

```json
{
  "round": {"id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10", "status": "finished", "finish_reason": "winner"},
  "player": {"state": "won"}
}
```

Этот ответ подтверждает только сохранённый исход раунда. Он не утверждает, что повторный вариант ответа был правильным, и не воспроизводит `guess`, `points_awarded`, `revealed_word`, `round_score` или `state_version`: этих данных `PrevGame` не хранит. Такая обработка возможна только пока соответствующий раунд остаётся в единственной записи `PrevGame`. 

Если повторный `/game/guess/` запрос после завершения раунда поступил от игрока, которому уже был возвращен ответ со значением `round.status=finished` и `player.state=lost` (другой игрок выиграл) или `round.finish_reason=timeout` (завершен по таймауту) - сервер до обычной проверки участия сверяет его `round_id` и идентификатор пользователя из JWT с `PrevGame.round_id` и `PrevGame.winner_user_id`. В данном случае идентификатор пользователя не будет совпадать с `PrevGame.winner_user_id`. Если предыдущая игра закончилась по таймауту - а) в переменной `PrevGame.winner_user_id` будет значение `None` (выигравшего игрока в предыдущем раунде не было - игра закончилась по таймауту); б) в переменную `PrevGame.winner_user_id` будет записан идентификатор ДРУГОГО пользователя (другой игрок выиграл в предыдущем раунде), в зависимости от этого, без изменения состояния и без повторной записи результата или начисления очков повторный `/game/guess/` возвращает HTTP `200` и JSON-ответ, соответствующий обычному ответу на этот запрос в ситуации, когда, соответственно, игра завершилась по таймауту или завершилась победой другого игрока, это означает, что сервер возвращает `round.id`, `round.status=finished`, `round.finish_reason` и `player.state=lost`, без полей guess, если исходную попытку воспроизвести нельзя. Условие должно применяться только когда `round_id` запроса совпадает с `PrevGame.round_id`; иначе запрос устарел и не должен получать исход другого раунда.   

`points_awarded` равен 10 × числу букв нормализованного ответа (пробелы и знаки пунктуации занимают клетки, но не дают очков), только если это первое правильное угадывание. Если слово уже решено другим участником, вернуть `result=already_solved`, `points_awarded=0`, раскрыть слово и обновить прогресс текущего игрока. Повтор правильного запроса не начисляет очки повторно.

Неверный ответ возвращает `result=incorrect` и не раскрывает слово. Ответ пользователя перед проверкой совпадения с загаданным словом кроме приведения сравниваемых слов к нижнему регистру и обрезки пробелов по краям, символ `ё` - ревращается в `е`, больше никак не нормализуется. Хорошей идеей было бы ограничение частоты попыток угадывания интервалом в секундах, заданным в конфигурации, с возвратом, например, статуса 429. Сообщения клиенту в случае `неудачи` - формируются на стороне фронтенда (в случае успешного угадывания слово просто `появляется` в соответствующих `квадратиках` кроссворда). 

Если путь игрока завершён по общим угаданным словам, сервер фиксирует единственного победителя под общим lock, добавляет его итоговый `round_score` в виде max(round_score, 0) к `users.score` и записывает один `game_results` в транзакции (т.е. отрицательный `round_score` не добавляется к результату - такой `round_score` приравниваем к нулю). Только этот победитель получает постоянные очки; очки остальных участников раунда при завершении не записываются. Следующий раунд создаётся сразу. 
Персональный экран победы/проигрыша, который демонстрируется на фронтенде с использованием js примерно 30 секунд, к статусам игрока никакого отношения не имеет.

### `POST /game/hint/`

Выдаёт один из двух видов подсказки для доступного игроку слова.

Запрос:

```json
{
  "round_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
  "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
  "hint_type": "first_letter"
}
```

`hint_type`: `first_letter` или `last_letter`, `unknown`. Подсказка открывает первую или последнюю букву слова; пробелы и знаки пунктуации не считаются буквами. Подсказка и стоимость применяются не более одного раза для данного игрока, типа подсказки и слова; повтор возвращает ту же подсказку и не повторяет списание. Используемые запросом `game/hint/`типы подсказок ограничены только значениями `first_letter` и `last_letter`. Значение `hint_type=unknown` может возвращаться только в ответе запроса и не является допустимым типом запрашиваемой подсказки.

Ответ включает вид подсказки, значение, списанные очки и текущий временный `round_score`. Значения стоимостей читаются из конфигурации; слово целиком никогда не возвращается. Если подсказка недоступна (пустое слово, игрок уже решил слово), сервер возвращает результат, в котором `hint_type=unknown` и остальные поля имеют пустые значения, без списания. Такой ответ должен интерпретироваться фронтендом как `Подсказка в данный момент недоступна`.

### `GET /game/sync/`

Периодически возвращает актуальную персональную проекцию игры и открытия на общих участках. Интервал polling задаётся в конфигурационном файле параметром `FRONTEND_SYNC_INTERVAL` (интервал между запросами в секундах) и может передаваться фронтенду посредством параметра context метода templates.TemplateResponse(...); клиент может передать `after_version` для определения изменений, но сервер всегда вправе вернуть полный snapshot. Отправляется только при статусе игрока `playing` - когда нужно согласовать угаданные разными слова на совпадающих участках и своевременно сообщить фротенду о завершении раунда. После этого фронтенд перестает отправлять его до тех пор, когда игрок уже в новом раунде начнет разгадывать кроссворд (перейдет в статус `playing`).  

Остановка же таймера на фронтенде при достижении нуля оставшихся секунд игры не останавливает polling : запрос `/sync/` продолжает отправляться на бэкенд до терминального ответа.

Пример query: `GET /game/sync/?round_id=...&after_version=15`

Ответ содержит `round.id` — идентификатор раунда, к которому относится snapshot, а также:

- актуальные `round.status`, `finish_reason`, `remaining_seconds`, `state_version`;
- `player.state`, назначенные города и выбранные участки;
- публичные размещения кроссворда игрока;
- для уже отгаданных слов — открытое написание и флаг первого угадавшего; для неотгаданных — только маску/длину и описание;

Sync не начисляет очки и не меняет владельца угаданного слова (и не завершает раунд по обнаруженному таймауту - механизмом завершения раунда по таймауту остается периодическая фонговая задача). Проверка дедлайна/фиксация окончания выполняется серверной логикой и под тем же механизмом синхронизации, что и другие операции состояния. 

Персональный экран результата - это событие, которое возникает однократно, как только асинхронный запрос `/guess/` или `/sync/` возвратил в ответе `"player": {"state": "won", "round_score": xx}` и, кроме этого, НЕ имеет никакого отношения к бэкенду (и не влияет на статусы, не является отдельным статусом), никак не меняет статусы на бэкенде (это js На фронтенде `демонстрирует` пользователю `кубок и конфетти` и `поезд`, что длится ПРИМЕРНО 30 секунд). В этот момент текущий раунд на бэкенде уже завершен, создан новый, в котором этого игрока - нет! Следовательно, если закрыть страницу и снова открыть в течение этих 30 секунд - это событие никак НЕ повторится (например запрос `/sync/` уже НЕ вернет `"player": {"state": "won", ...}` - так как в только что созданном раунде этого игрока еще не существует). Состояние игрока `player.state = watching_stats`. Ему демонстрируется статистика игр.  

Чтобы бэкенд мог сообщить участнику о завершении раунда, `PrevGame` хранит в памяти `round_id`, `winner_user_id` и `finish_reason` последнего завершённого раунда. Экземпляр создаётся один раз в lifespan и сохраняется в `app.state`; при завершении раунда эти поля обновляются до создания следующего раунда. В MVP `PrevGame` хранит только один раунд: завершение следующего раунда перезаписывает предыдущую запись. Поэтому, если клиент не успел получить результат предыдущего раунда до завершения ещё одного, этот результат ему не гарантируется; запрос фронтенда со старым `round.id` (передается в запросе как плоский параметр `round_id`) считается устаревшим и не получает исход другого раунда. Если предыдущий раунд завершился по таймауту, в переменную `winner_user_id` следует записать значение None. Это позволит, при повторном запросе, отличить раунд, зхавершенный по таймауту от рауда, завершенного победой другого игрока. 

`player.state=lost` при обращении к `PrevGame` предназначен для штатного потока клиента: `/game/sync/` отправляет участник, который находится в состоянии `playing` в завершившемся раунде и ещё не получил терминальный ответ. После получения такого ответа фронтенд прекращает polling и переходит к статистике. Для MVP сервер не хранит список участников завершившегося раунда и не проверяет членство пользователя в нём; контракт не гарантирует персональный исход для произвольных запросов к старым раундам вне этого клиентского потока.

При обработке `/game/sync/` сервер сверяет переданный клиентом `round_id` с идентификатором раунда: если это `round_id` из `PrevGame`, ответ сообщает `round.status=finished`, соответствующий `finish_reason` и персональный исход в рамках описанного штатного потока; если это идентификатор текущего раунда, сервер возвращает состояние текущего раунда и не использует `PrevGame`. Запрос с идентификатором, который не соответствует ни текущему, ни последнему завершённому раунду, считается устаревшим и не должен получать исход другого раунда.

Фронтенд перед применением ответа `/game/sync/` обязан сравнить `round.id` в ответе с `round.id` раунда, который сейчас отображается. Если идентификаторы не совпадают, ответ считается запоздавшим и игнорируется целиком: он не должен менять состояние игрока, кроссворд, счёт или версию состояния. `state_version` сравнивается только между ответами одного и того же `round.id`. Это предотвращает применение ответа старого раунда после перехода пользователя к новому.

Чтобы фронтенд не получил противоречивые исходы, если запрос `/sync/` придёт позже ответа `/guess/`, бэкенд проверяет, совпадает ли `winner_user_id` с `user_id` отправившего запрос: победителю возвращается `player.state=won`, остальным участникам — `player.state=lost`. Дополнительно фронтенд не применяет запоздавший ответ `/sync/`, если к моменту его обработки уже перешёл из `playing` в `watching_stats`.

## 5. Серверные инварианты

1. В каждый момент принимается не более одного победителя на раунд.
2. Для общего участка существует одно состояние слова на раунд: первое правильное угадывание фиксируется один раз; все участники этого участка видят открытие и считают слово пройденным.
3. `placement_id` доступен только участнику, чья проекция содержит слово; идентификатор не даёт прочитать отгадку.
4. Сервер проверяет дедлайн до обработки guess/hint/join/route. Запрос, пришедший после `expires_at`, не может изменить очки или прогресс.
5. Только победа создаёт `GameResult` и изменяет постоянный `users.score`. Таймаут без победителя не создаёт строку результата.
6. Все действия, влияющие на состояние одного процесса MVP, сериализуются общим lock. Перед запуском нескольких worker/реплик lock в памяти недостаточен: активное состояние и координацию нужно перенести в Redis.
7. Рейтинг и `users.score` отражают только зафиксированные победы согласно выбранному правилу `winner_only`.

## 6. Восстановление страницы и срок результата

После авторизации backend восстанавливает состояние участника по JWT user ID и текущему раунду:

- нет записи участника — `watching_stats`;
- города назначены, путь не подтверждён — `selecting_route`;
- путь подтверждён, раунд активен — `playing`;
- пользователь победил/проиграл только что завершившийся раунд — `watching_stats` (при этом примерно 30 секунд демонстрируется при помощи js экран Победы/Поражения, который к статусам никакого отношения не имеет).

## 7. Что намеренно не входит

- WebSocket/SSE; синхронизация выполняется polling через `/game/sync/`.
- Публичный доступ к ответам, email или другим приватным данным.
- Персистентные записи каждого действия или состояния активной игры в PostgreSQL.
- Масштабирование на несколько процессов до внедрения Redis.

## 8. Принятые решения по вопросам перед реализацией

1. **Нормализация ответа:** регистр, пробелы, дефисы и эквивалентность `ё`/`е`; применять ли Unicode NFC.
- Решение: Применение Unicode NFC для нормализации ответа считаю излишним. Достаточно: обрезать пробелы по краям, привести к нижнему регистру сравниваемые слова, заменить `ё` на `е`. 

2. **Защита от перебора:** лимит неверных ответов по слову/пользователю и rate limit для guess/hint.
- Решение: Да, отличная идея! а) Нужно ограничить частоту запросов guess интервалом в секундах из конфигурационного файла (подробнее описано ниже); б) Ограничивать количество неверных ответов - не нужно. в) Устанавливать rate limit и ограничивать количество запросов для запроса `/hint/` - не нужно.

3. **Счёт:** может ли временный `round_score` стать отрицательным после подсказок; если да, как обрабатывать отрицательную награду победителя при ограничении `users.score >= 0`.
- Решение: временный `round_score` может стать отрицательным, но если, при этом, зафиксирована победа игрока в текущем раунде, а итоговый счет оказался отрицательным - он `обнуляется`, приравнивается к нулю. В этом случае, игрок побеждает с нулевым результатом.    

4. **Выбор слов при нехватке каталога:** что делать, если для маршрута/общего участка нельзя подобрать слова требуемой длины; какие `409`/`503` коды и возможность сменить путь. 
- Решение: Если последнее слово из нескольких слов или единственное слово нужной длины на участке пути НЕ получается подобрать для этого участка - этот участок пути остается пустым (без слов кроссворда) или, в случае нескольких слов, на этом участке остается больше `пустого места`, интервалов между оставшимися словами кроссворда на этом участке. Если какой-либо участок остался пустым - он сразу же помечается (автоматически) пройденным. Перед возвратом фроненду ответа именно бэкенд должен проверять, что хотя бы один участок всего пути от начального до конечного города оказался НЕпустым. Если все участки маршрута пусты - бэкенд должен записать в журнал ошибку crossword_generation_failed, сменить игроку статус на `watching_stats` (на сервере - убрать его из PlayerGameState, ActiveGame.players и освободить назначенную ему пару городов) и возвратить ошибку 503 и выдать ошибку в теле ответа: 
{
  "error": {
    "code": "crossword_generation_failed",
    "message": "Не удалось подготовить маршрут. Попробуйте войти в игру чуть позже"
  },
  "round": {"status": "active"},
  "player": {
    "state": "watching_stats"
  }
}  

Если ответ потеряется и клиент повторит `/game/route/` к этому моменту статус данного игрока на бэкенде уже не будет `selecting_route` и на такой запрос нужно сразу выдавать в ответ ошибку 404, с последующей сменой на фронтенде статуса игрока на `watching_stats` - ему демонстрируется блок статистики.

При этом условие «весь маршрут пустой» следует считать критическим нарушением игрового инварианта: сервер должен записать событие с уровнем CRITICAL и поднять сигнал мониторингу. Клиенту — вернуть безопасное сообщение без внутренних подробностей.
 
5. **Назначение городов:** подтвердить правило, что запрещена только повторная неориентированная пара, а отдельный город может встречаться в парах разных игроков; определить поведение при исчерпании допустимых пар. 
- Решение: a) запрещена только повторная неориентированная пара b) К сожалению, для MVP, в этом случае - вернуть явную ошибку `409 city_pairs_exhausted` и возвратить игрока в состояние `watching_stats`, `round.status` при этом, не меняет своего значения. В следующей версии предполагается выбор из нескольких карт (например: Азия, Северная Америка, Южная Америка, ... Корусант, Мандалор, Аракис и т.д.), при истощении городов на выбранной игроком карте, ему будут предложены другие карты взамен.

6. **Срок результата:** подтвердить 30 секунд и решить, должен ли повторный вход в эти 30 секунд снова показывать экран результата или сразу показывать статистику.
- Решение: При повторном входе в эти 30 секунд - сразу показывать статистику (игрок сразу переходит в состояние `watching_stats`, а демонстрация Экрана Победы/Поражения к статусу игрока не имеет, просто длится примерно 30 сек. на странице игрока).

7. **Polling:** задать интервал `/game/sync/` и максимальную частоту запросов.
- Решение: Установить `Rate limit` на запросы `/guess/` одного пользователя. При превышениии `Rate limit` возвращать фронтенду ошибку 429. При повторном превышении - просто продолжнать возвращать 429.
Нужно записывать интервал `/game/sync/` и `Rate limit` на запросы `/guess/` одного пользователя в конфигурационный файл и брать из этого (.env) файла. Имена будут называться USER_GUESS_RATE_LIMIT (число запросов `/guess/` данного игрока в минуту) и FRONTEND_SYNC_INTERVAL (в секундах). При превышении USER_GUESS_RATE_LIMIT можно возвращать фронтенду ошибку 429 Too Many Requests, и добавить в HTTP-заголовок параметр Retry-After.
Retry-After <вычисляемое время до следующей допустимой попытки>. 

8. **Подсказки:** подтвердить повторный запрос без повторного списания как выбранную политику и определить код ошибки, если подсказка неприменима.
- Решение: Да, повторный запрос одной и той же подсказки возвращается без повторного списания. Допустимые запрашиваемые типы — `first_letter` и `last_letter`; `unknown` используется только в ответе, если подсказка недоступна, например, слово уже разгадано.

9. Фронтенду не нужно знать точные координаты прямоугольников на отрезке. `position_index` определяет только порядок расположения прямоугольников на отрезке. Как расположить дочерние блоки слов с прямоугольниками букв равномерно внутри внешнего блока, идущего от одного конца отрезка (одного города) - к другому концу (другому городу) - это дело CSS ( flexbox ? ). Сервер, таким образом, возвращает индекс порядка. Размер пробелов между словами не важен.
