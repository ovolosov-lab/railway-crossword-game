# ADR 0009: API-контракт непрерывной игры

- **Статус:** согласован
- **Дата первоначального контракта MVP:** 2026-10-28
- **Дата последнего обновления:** 2026-11-18
- **Область:** HTTP API игровой страницы `game.html`
- **Связанные решения:** [ADR 0005 — контракт MVP](./0005-game-api-contract.md), [ADR 0007 — непрерывные сессии игроков](./0007-continuous-game-player-sessions.md), [диаграмма состояний пользователя](./0008-state-transition-diagram-user.md)

**Применимость:** контракт согласован для следующей версии непрерывной игры. Он реализован в `backend/app/continuous_game_api.py` и включается настройкой `CONTINUOUS_GAME_ENABLED=true` (требует `REDIS_URL`); по умолчанию остаётся API MVP, описанный в [ADR 0005](./0005-game-api-contract.md), пока фронтенд (задача 40) не переведён на новый контракт. Раздел 8 сохраняет историю обсуждения; уточнения, принятые после него, отражены в основных разделах.

## 1. Цель и принятые решения

Этот документ задаёт JSON API для непрерывной игры. Основные положения ADR 0007:

1. `POST /game/join/` назначает города; затем игрок может выбрать путь вручную или запросить автоматический вариант через `POST /game/route/auto/`. Только `POST /game/route/` подтверждает путь и запускает игру участника.
2. Успешные запросы возвращают 2xx, ошибки используют подходящие HTTP-коды и JSON-ответ с машинным кодом ошибки. Ошибки не маскируются статусом `200`.
3. Промежуточный счёт хранится в Redis до завершения индивидуальной сессии. При подтверждённой победе её результат записывается в `game_results`, а очки добавляются к `users.score` в одной транзакции PostgreSQL. При сдаче очки текущей сессии сгорают, запись победы не создаётся.


## 2. Общие правила

- Базовые пути ниже приведены без глобального `/api` префикса, чтобы сохранить адреса, уже перечисленные в ADR.
- Игровые страницы и endpoints требуют авторизации. Пользователь определяется только по JWT в HttpOnly cookie; клиент не передаёт `user_id` как источник идентичности.
- JSON-запросы используют `Content-Type: application/json`; ответы — `application/json`.
- Значения `error.code` стабильны и не зависят от языка. `error.message` и другие сообщения выбираются из локализованных JSON-ресурсов для настроенного `LANGUAGE=ru/en`; тексты примеров могут уточняться без изменения машинных кодов.
- Все cookie-запросы, изменяющие состояние, защищены CSRF-токеном независимо от способа доступа к странице. JWT не возвращается в JSON и не помещается в URL.
- Идентификаторы сессии (`session_id`, `session.id`) и игрового слова (`placement_id`) непрозрачны для клиента. `placement_id` не содержит текст ответа.
- В телах запросов, относящихся к сессии, его идентификатор передаётся плоским полем `session_id`. В ответах идентификатор входит в объект `session` под именем `id` (`session.id`).
- Ни один ответ API не раскрывает `word_text` до того, как соответствующее слово отгадано. Синхронизация может раскрыть уже угаданное слово на совпадающем участке маршрута.
- `route_ids` в запросе подтверждения передаются в порядке прохождения пути. Сервер повторно проверяет принадлежность рёбер каталогу, непрерывность, концы пути, отсутствие повторных рёбер и циклов.
- `session.state_version` — монотонно растущая версия персонального состояния, включая открытия общих слов, счёт и переход к фиксации или победе. Она возвращается во всех проекциях существующей сессии и увеличивается, когда меняются отображаемые данные сессии. Клиент сравнивает версии только одной `session.id` и игнорирует более старые ответы; `won` не откатывается в нетерминальное состояние той же сессии.
- В отсутствие сессии `session` равен `null`, а `player.state` — `watching_stats`; отсутствие или недоступность Redis нельзя представлять так, будто сессии нет.
- В проекциях существующей сессии `player` содержит `state` и `session_score`; в состоянии выбора маршрута начальный счёт равен `0`. В проекциях маршрута также передаются назначенные города и выбранные `route_ids`, а в кроссворде для каждого слова — полученные игроком подсказки, необходимые для восстановления страницы.
- Проверка и изменение общего состояния координируются между процессами атомарными операциями Redis, а не только `asyncio.Lock`. Фиксация победы в PostgreSQL выполняется отдельно, с защитой от повторного начисления по ID сессии.
- Повтор запроса не должен повторно назначать города, засчитывать одно слово или списывать стоимость уже использованной подсказки. Идемпотентность обеспечивается состоянием участника и записи слова/подсказки; если клиентский retry нельзя распознать по ресурсу, запрос дополнительно принимает `Idempotency-Key`.
- Для `/join/` и `/surrender/` обязателен заголовок `Idempotency-Key`: случайный UUID, новый для каждого намеренного действия и тот же при повторе запроса. Записи в Redis связываются с авторизованным пользователем, операцией и игровым поколением. Повторное использование ключа той же операции с другим телом запрещено и возвращает `409 idempotency_key_conflict`. Ключ сам по себе не подтверждает авторизацию.
- Клиент сохраняет ключ и тело незавершённого действия для повтора после сетевой ошибки или перезагрузки. Ответ присоединения принимается только для ожидаемого намерения; запоздавший ответ старого присоединения не заменяет уже отображаемую новую сессию.
- Первая правильная отгадка открывает слово всем игрокам общего участка и начисляет очки только отгадавшему. Она может завершить сразу несколько маршрутов; каждая такая сессия становится победившей независимо, после собственной фиксации результата. Сессии, чьи маршруты ещё не завершены, продолжают игру.

### Состояния в API

`session.status`:

- `active` — сессия принимает действия, допустимые её состоянию;
- `finishing` — маршрут завершён, фиксация победы ещё не подтверждена; это не подтверждённая победа;
- `finished` — победа подтверждена и сохранён её снимок; `finish_reason` равен `winner`.
  
`player.state`:

- `watching_stats` — нет активной сессии и сохранённой победы;
- `selecting_route` — города назначены, путь ещё не подтверждён;
- `playing` — путь подтверждён, кроссворд создан;
- `finishing` — идёт подтверждение победы; сдаваться и создавать новую сессию нельзя;
- `won` — победа подтверждена, сессия сохранена как неактивная. Игрок видит экран победы с разгаданным кроссвордом до присоединения к новой игре; polling этой сессии прекращается.
- Сдача завершает активную сессию без победы; подтверждение сдачи хранится отдельно от активной сессии.

Для `active` и `finishing` поле `session.finish_reason` равно `null`. Статусы окончания общего раунда, включая `closed_other_winner`, не используются.

Анимация победы длится примерно 30 секунд и не задерживает изменение состояния. Она запускается, если на той же открытой странице игрок перешёл из `playing` в `won`, в том числе через `finishing`. Если страница восстановлена сразу в `finishing` или `won`, анимация не запускается. После анимации экран победы и разгаданный кроссворд остаются до присоединения к новой игре; после перезагрузки экран восстанавливается.

## 3. Формат ошибок

Для ошибки возвращается объект:

```json
{
  "error": {
    "code": "route_not_connected",
    "message": "Выбранные участки не образуют непрерывный путь между назначенными городами.",
    "details": null
  }
}
```

Использовать HTTP-коды по смыслу:

| HTTP | Когда |
|---|---|
| `400` | Некорректный формат запроса, который нельзя разобрать как JSON |
| `401` | Нет действующей авторизации |
| `403` | Действие запрещено для текущего участника, в том числе недостаточно очков для новой подсказки |
| `404` | Сессия или `placement_id` не найден либо не принадлежит доступному состоянию авторизованного пользователя |
| `409` | Конфликт состояния: активная сессия отсутствует, игрок уже выбрал несовместимый путь, повторный запрос конфликтует с сохранённым выбором |
| `422` | JSON синтаксически корректен, но тело или query-параметры не прошли валидацию |
| `429` | Превышен лимит запросов, если он включён |
| `500` / `503` | Неожиданная ошибка приложения или временная недоступность сервиса |

Ошибки игровых состояний должны содержать стабильный `error.code` и при необходимости актуальные `session` и `player` projections, чтобы интерфейс мог перейти в правильное состояние. API-запрос авторизации возвращает `401` JSON, а не HTML redirect; redirect с flash-сообщением применяется при навигации браузера на защищённую HTML-страницу.

Обязательные поля ошибки — `error.code`, `error.message` и `error.details` (`null`, если подробностей нет). Ниже примеры машинных кодов и русских сообщений; английские сообщения берутся из тех же локализованных ресурсов.

| HTTP | `error.code` | Пример сообщения |
|---|---|---|
| `401` | `authentication_required` | Требуется авторизация. |
| `403` | `insufficient_points` | Для получения подсказки недостаточно очков. |
| `404` | `session_not_found` | Игровая сессия не найдена. |
| `409` | `route_already_solved` | Маршрут уже разгадан. Выберите другой маршрут. |
| `409` | `no_available_route` | Не удалось подобрать доступный маршрут. |
| `409` | `victory_finishing` | Победа ещё сохраняется. Повторите попытку позже. |
| `409` | `idempotency_key_conflict` | Ключ запроса уже использован с другими данными. |
| `409` | `join_result_unavailable` | Результат прежнего присоединения больше недоступен. |
| `503` | `game_state_unavailable` | Игровое состояние временно недоступно. |
| `503` | `crossword_generation_failed` | Не удалось создать кроссворд. Присоединитесь к игре заново. |

При отсутствии указанной сессии сервер не возвращает чужие данные или состояние новой сессии под старым ID. Клиент не переключается на статистику по запоздавшей ошибке старого запроса, если уже отображает новую сессию; при неопределённости он повторно получает текущее состояние авторизованного пользователя.

## 4. Endpoints

Примеры разных endpoints иллюстративны и не обязательно изображают одну последовательность действий, даже если используют одинаковые идентификаторы. Три примера `/sync/` ниже показывают последовательные состояния одной сессии.

### `GET /game/stats/`

Возвращает состояние текущей сессии пользователя и публичную статистику победителей. Требует авторизации, но не присоединяет пользователя к игре, не создает ему новую сессию.

Пример:

```json
{
  "session": null,
  "player": {
    "state": "watching_stats"
  },
  "participant_count": 8,
  "leaderboard": [
    {"username": "player_one", "score": 1240}
  ]
}
```

Рейтинг строится по `users.score`; в него входят только зафиксированные победы. `participant_count` — число активных сессий, включая фиксацию победы, но не сохранённые победы. Если сессия существует, возвращаются её ID, статус, причина завершения и версия, а также соответствующее состояние игрока. Не возвращать email, хэш пароля, JWT и другие приватные данные.

### `GET /game/routes/`

Возвращает карту доступных участков и персональную игровую проекцию. Endpoint нужен для отрисовки карты и восстановления страницы после перезагрузки; он не создаёт новую сессию. Для `selecting_route` возвращаются назначенные города, для `playing` — также маршрут и публичный кроссворд; для `finishing` — состояние фиксации без сообщения о подтверждённой победе. Для сохранённого `won` возвращается снимок разгаданного кроссворда, включая открытые слова. Названия городов выбираются по `LANGUAGE`.

Основное содержимое:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "finish_reason": null,
    "state_version": 14
  },
  "player": {
    "state": "selecting_route",
    "session_score": 0,
    "source_city_id": 1,
    "target_city_id": 2,
    "route_ids": []
  },
  "cities": [
    {"id": 1, "name": "Лондон", "top": 1405, "left": 779},
    {"id": 2, "name": "Дублин", "top": 1224, "left": 465}
  ],
  "routes": [
    {"id": 1, "source_city_id": 1, "target_city_id": 2, "length_in_letters": 14}
  ]
}
```

Координаты маршрутов на клиенте выводятся из координат городов и карты; они не заменяют серверную проверку пути.

### `POST /game/join/`

Создаёт активную сессию пользователя в состоянии `selecting_route` и назначает пару городов. Тело запроса пустое. Заголовок, например: `Idempotency-Key: 213cc4ef-31c9-46d3-a93f-39a3c4a60d4b`.

- Если у пользователя уже есть активная сессия, вернуть его текущее состояние без повторного назначения и создания новой сессии.
- В состоянии фиксации победы новую сессию создавать нельзя. После подтверждённой победы явное присоединение создаёт новую сессию с новым ID и заменяет сохранённый снимок победы.
- Не назначать ту же неориентированную пару городов, которая уже выдана другому игроку; хотя бы один город пары должен различаться с каждой ранее выданной парой.

Для нового намерения фронтенд создаёт новый случайный ключ; для повтора из-за потерянного ответа использует прежний. Ключ и результат успешного присоединения хранятся в Redis в течение игрового поколения. Создание или обнаружение активной сессии и запись связи ключа с её ID согласуются атомарно между конкурентными запросами. Разные ключи из нескольких вкладок не обходят ограничение одной активной сессии.

Повтор с тем же ключом не создаёт новую сессию, даже если исходная уже победила. Пока исходная сессия доступна, возвращается её актуальное состояние; если она уже заменена или удалена, возвращается `409 join_result_unavailable`, без создания новой игры и без выдачи состояния новой сессии под старым ID. При потере Redis или смене поколения гарантия распознавания прежнего ключа не сохраняется. Клиент хранит ключ незавершённого запроса для безопасного повтора, в том числе после перезагрузки страницы.

Успешный ответ:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "finish_reason": null,
    "state_version": 1
  },
  "player": {
    "state": "selecting_route",
    "session_score": 0,
    "source_city_id": 1,
    "target_city_id": 29,
    "route_ids": []
  }
}
```

При отсутствии доступной уникальной пары вернуть явную ошибку `409 city_pairs_exhausted`, не создавая сессию. Игрок остаётся на статистике либо на сохранённом экране победы, если пытался начать новую игру из `won`: неуспешная попытка не удаляет снимок.

### `POST /game/route/auto/`

Возвращает случайный простой путь от назначенного города отправления до города назначения. Запрос защищён CSRF и принимает идентификатор сессии:

```json
{
  "session_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10"
}
```

Сервер проверяет активность сессии и состояние игрока, затем ищет путь без повторения городов. Автоподбор исключает маршруты, которые на момент подбора целиком состоят из уже отгаданных слов общих участков. Отдельные пустые участки допускаются, но полностью пустой путь не может быть принят. Ответ содержит `session`, `player` и упорядоченный `route_ids`; найденный путь не сохраняется и не подтверждается. Клиент отображает его на карте, после чего игрок отдельно вызывает `POST /game/route/`. Если подходящего пути нет, возвращается `409 no_available_route`, не утверждающий, что назначенные города обязательно разъединены. Поскольку состояние общих слов может измениться после автоподбора, сервер повторно проверяет маршрут при подтверждении.

### `POST /game/route/`

Подтверждает непрерывный путь и создаёт персональную проекцию кроссворда.

Запрос:

```json
{
  "session_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
  "route_ids": [1, 3, 5]
}
```

Сервер проверяет активность сессии, состояние игрока, непрерывность в указанном порядке, использование назначенных городов как двух концов, отсутствие циклов и повторов, а также наличие слов для формирования кроссворда (отдельные (не все сразу) участки, в связи со слишком маленьким расстоянием между точками-городами, могут остаться без слов - такое допускается; просто эти участки будут сразу помечены как пройденные). Проверка на клиенте служит только UX.

Если непустой путь целиком состоит из уже отгаданных слов общих участков, сервер не подтверждает его, не начисляет очки и возвращает `409 route_already_solved`, предлагая выбрать другой путь. Сессия остаётся в состоянии выбора. Это не ошибка полностью пустого кроссворда.

Для принятого пути сервер создаёт размещения на постоянных участках маршрутов. Если общий участок уже имеет слова у других игроков с активными сессиями, повторно использует их и общее состояние угаданности; иначе назначает слова из каталога. Угаданное слово открывается участникам с общим участком, но очки за его отгадывание начисляются только первому угадавшему.

Для размещения используется `offset_px` — неотрицательное числовое смещение начала слова вдоль участка от города `source_city_id` соответствующей записи маршрута, в пикселях исходной карты. Направление одинаково для всех игроков, даже если они проходят участок в обратную сторону. Масштабирование карты на экране применяется ко всему участку и словам вместе; оно не изменяет сохранённые смещения. `position_index` из прежнего контракта не используется для вычисления положения.

Каждый символ `word_text`, включая пробелы и знаки пунктуации, занимает ячейку шириной 26 пикселей. Между соседними словами оставляется не менее 5 пикселей; максимальный промежуток жёстко не задан. Доступная длина для размещения — меньшая из `геометрической длины участка исходной карты минус 52` и `length_in_letters * 26 - 52` пикселей. Слова и промежутки не выходят за эти пределы.  С каждой стороны должен оставаться отступ не менее 26 пикселей, чтобы буква слова не пряталась под кружок города. Для участков вместимостью до 31 ячейки включительно цель — не более 52 пикселей общего свободного пространства; для больших — не более 78 пикселей. В свободное пространство входят промежутки и остатки по краям доступной длины. Это цель, а не гарантия: если словарь, минимальные промежутки или правила уменьшения числа двухбуквенных (и однобуквенных) слов не позволяют её достичь, допускается большее свободное пространство. Остаток распределяется равномерно между словами; для одного слова его можно разместить по центру доступной длины. При повторном использовании общего участка сохраняются те же слова и смещения. Но, с каждого конца в промежутке между городами должен оставаться отступ, равный 26 px. 

Участок, на котором не помещается ни одного подходящего слова, остаётся пустым и считается пройденным; если пуст весь выбранный путь, сервер удаляет участие и освобождает пару городов, а затем возвращает `503 crossword_generation_failed`.

Успешный ответ содержит только публичное представление размещений:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "finish_reason": null,
    "state_version": 15
  },
  "player": {"state": "playing", "session_score": 0, "source_city_id": 1, "target_city_id": 29, "route_ids": [1, 3, 5]},
  "crossword": [
    {
      "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
      "route_id": 1,
      "offset_px": 0,
      "letter_count": 6,
      "definition": "Описание слова без его отгадки.",
      "is_guessed": false,
      "guessed_by_me": false,
      "hint_types_used": [],
      "hints": []
    }
  ]
}
```

Для неотгаданных слов не включать `word_text`, `normalized_word` или иной материал, из которого можно восстановить отгадку. Уже отгаданные общие слова возвращаются открытыми.

Каждое размещение содержит `placement_id`, `route_id`, `offset_px`, `letter_count` (число ячеек), `definition`, `is_guessed`, `guessed_by_me`, `hint_types_used` и `hints`. `word_text` присутствует только у отгаданных слов. `hints` содержит персонально полученные подсказки вида `{"hint_type": "first_letter", "value": "П"}`; `hint_types_used` перечисляет те же типы. Для отсутствующих подсказок оба массива пусты. Эти данные включаются и в проекции для восстановления, в том числе в `/sync/` и снимок победы.

Маршрут подтверждается на бэкенде только один раз. Если ответ на успешное подтверждение не дошёл до фронтенда и тот всё ещё находится в `selecting_route`, он может повторить тот же запрос с прежними `session_id` и `route_ids`. Если маршрут уже подтверждён, повторный запрос не подтверждает его заново: сервер возвращает актуальные данные этой сессии, необходимые фронтенду для восстановления состояния, включая те же `placement_id`. Повтор не меняет счёт и не генерирует участки заново. Конкурентные одинаковые запросы также не должны приводить к нескольким подтверждениям.

Фронтенд применяет ответ с учётом идентификатора сессии и версии; если он уже покинул `selecting_route`, повторный ответ не запускает игру заново. Попытка заменить подтверждённый путь — `409 route_already_confirmed`; изменение пути после начала разгадывания не поддерживается. Если за время повтора сессия перешла к фиксации или победе, ответ отражает её актуальное состояние, а не возвращает игрока к статистике; при `won` снимок запрашивается отдельно через `/sync/` или `/routes/`. После `503 crossword_generation_failed` клиент возвращает пользователя к статистике и предлагает присоединиться заново: прежнее участие уже удалено, пара городов освобождена.


### `POST /game/guess/`

Проверяет ответ участника и, если он правильный, атомарно отмечает общее слово угаданным.

Запрос:

```json
{
  "session_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
  "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
  "answer": "пример"
}
```

Ответ при правильной отгадке:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "finish_reason": null,
    "state_version": 16
  },
  "player": {"state": "playing", "session_score": 60},
  "guess": {
    "result": "correct",
    "already_solved": false,
    "points_awarded": 60,
    "revealed_word": "ПРИМЕР"
  }
}
```

За первую правильную отгадку начисляется 10 очков за каждую букву загаданного слова. Пробелы, дефисы, тире и другие знаки пунктуации очков не дают, хотя занимают ячейки. Для подсчёта букв исходное слово приводится к Unicode NFC; считаются символы категорий Unicode `L`. Например, «Нью-Йорк» занимает восемь ячеек и приносит 70 очков. `letter_count` обозначает число ячеек и не используется как число букв для начисления.

Если слово уже открыто, а сессия всё ещё в состоянии `playing`, запрос возвращает HTTP `200` без повторного начисления и без изменения состояния только вследствие этого запроса. Это правило действует независимо от того, открыл слово сам игрок или другой участник. Ответ не утверждает, что присланный вариант правильный; `session_score` содержит актуальный счёт:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "finish_reason": null,
    "state_version": 16
  },
  "player": {"state": "playing", "session_score": 60},
  "guess": {
    "result": "already_solved",
    "already_solved": true,
    "points_awarded": 0,
    "revealed_word": "ПРИМЕР"
  }
}
```

Для запроса в состоянии `finishing` возвращается актуальное состояние фиксации без повторного начисления; после подтверждённой победы действует правило терминального ответа ниже.

Ответ при победе данного игрока:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "finished",
    "finish_reason": "winner",
    "state_version": 18
  },
  "player": {"state": "won", "session_score": 460},
  "guess": {
    "result": "correct",
    "already_solved": false,
    "points_awarded": 90,
    "revealed_word": "ШРЕДИНГЕР"
  }
}
```

`session.id` в успешном ответе всегда равен `session_id` в запросе, даже если найдена сохранённая победа. Если финальная отгадка уже принята, но PostgreSQL ещё не подтвердил результат, сервер возвращает состояние `finishing`, не сообщает `won` и продолжает безопасную фиксацию. Клиент продолжает узнавать результат через `/sync/`.

Пример HTTP `200`, когда принята последняя отгадка, но победа ещё фиксируется:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "finishing",
    "finish_reason": null,
    "state_version": 17
  },
  "player": {"state": "finishing", "session_score": 460},
  "guess": {
    "result": "correct",
    "already_solved": false,
    "points_awarded": 90,
    "revealed_word": "ШРЕДИНГЕР"
  }
}
```

Если повторный `/game/guess/` поступил после завершения сессии, т.е. сессия не найдена на бэкенде - бэкенд возвращает HTTP `404` с соответствующим сообщением об ошибке. При совпадении `session_id` с id сохраненной сессии - без изменения состояния и без повторной записи результата или начисления очков возвращает HTTP `200` с терминальным исходом победителя:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "finished",
    "finish_reason": "winner",
    "state_version": 18
  },
  "player": {"state": "won", "session_score": 460}
}
```

Этот ответ подтверждает только сохранённый исход сессии. Он не утверждает, что повторный вариант ответа был правильным, и не воспроизводит `guess`, `points_awarded` или `revealed_word`. Для экрана победы клиент получает сохранённый снимок через `/game/routes/` или `/game/sync/`. При `404` клиент учитывает ID запроса и правила обработки устаревших ответов из раздела 3.

Неверный ответ для ещё не открытого слова возвращает `result=incorrect` и не раскрывает слово. Перед сравнением ответ пользователя и загаданное слово одинаково нормализуются:

1. Приводятся к Unicode NFC и нижнему регистру; для русского языка `ё` заменяется на `е`.
2. Удаляются все пробельные символы Unicode (`White_Space`), в том числе обычные и неразрывные пробелы, как по краям, так и внутри фразы.
3. Удаляются дефис `-` (U+002D) и символы U+2010–U+2015: дефисы, неразрывный дефис и варианты тире `‒`, `–`, `—`, `―`, независимо от их положения во фразе. Остальные знаки не удаляются.

Например, для сравнения «Нью-Йорк», «НЬЮ — ЙОРК» и «ньюйорк» дают `ньюйорк`. Исходное написание загаданного слова при этом не изменяется и после отгадки показывается игроку в исходном виде. Сообщения при неверном ответе формируются на фронтенде.

Если путь игрока завершён по общим угаданным словам, сервер согласованно переводит каждую затронутую сессию в `finishing`. Для каждой отдельно записывает `game_results` и добавляет `max(session_score, 0)` к `users.score` в одной транзакции; уникальный ID сессии предотвращает повторное начисление. Лишь после подтверждения транзакции публикуется `finished`/`won`. При сбое или неизвестном результате commit обработка безопасно повторяется по ADR 0007.

### `POST /game/hint/`

Выдаёт один из двух видов подсказки для доступного игроку слова.

Запрос:

```json
{
  "session_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
  "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
  "hint_type": "first_letter"
}
```

В запросе `hint_type` принимает только `first_letter` или `last_letter`; `unknown` допустим только в ответе о недоступной подсказке. Подсказка открывает первую или последнюю букву слова; пробелы и знаки пунктуации не считаются буквами. Подсказка и стоимость применяются не более одного раза для данного игрока, типа подсказки и слова; повтор возвращает ту же подсказку и не повторяет списание.

Ответ включает вид подсказки, значение, списанные очки и текущий временный `session_score`. Значения стоимостей читаются из конфигурации; слово целиком никогда не возвращается. Если новая подсказка недоступна (например, слово уже отгадано), сервер возвращает результат, в котором `hint_type=unknown` и остальные поля имеют пустые значения, без списания. Такой ответ должен интерпретироваться фронтендом как `Подсказка в данный момент недоступна`.

Для ранее полученной подсказки проверка повторного получения выполняется до проверки баланса и доступности новой подсказки: повтор бесплатен, пока существует состояние сессии. Если стоимость новой подсказки сделает текущий счёт отрицательным, сервер не выдаёт букву и не списывает очки; возвращается HTTP `403` с кодом `insufficient_points`. Проверка баланса, выдача и списание атомарны, в том числе при конкурентной чужой отгадке.

Пример HTTP `200` при выдаче новой подсказки; `points_charged` — сумма, списанная именно этим запросом:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "finish_reason": null,
    "state_version": 16
  },
  "player": {"state": "playing", "session_score": 50},
  "hint": {
    "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
    "hint_type": "first_letter",
    "value": "П",
    "points_charged": 10
  }
}
```

Для бесплатного повтора `points_charged` равен `0`, `value` сохраняется, а счёт и версия не изменяются только вследствие этого повтора. Для недоступной новой подсказки HTTP `200`: `hint_type` равен `unknown`, `value` равен `null`, `points_charged` равен `0`; остальные поля ответа имеют ту же форму.

Пример HTTP `403` при недостатке очков:

```json
{
  "error": {
    "code": "insufficient_points",
    "message": "Для получения подсказки недостаточно очков.",
    "details": null
  }
}
```

При `LANGUAGE=en` сообщение для этого кода: `Not enough points to get a hint`.

### `POST /game/surrender/`

Завершает активную сессию пользователя по кнопке «Сдаюсь!», доступной как при выборе маршрута (`selecting_route`), так и при разгадывании (`playing`). Запрос защищён CSRF и передаёт `Idempotency-Key` в заголовке. При повторе используется тот же ключ и то же тело:

```json
{
  "session_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10"
}
```

Сервер проверяет владельца и состояние сессии, атомарно согласует сдачу с победой и новой игрой, завершает сессию, освобождает пару городов и ссылки на участки и сохраняет подтверждение для повтора. Очки текущей сессии сгорают; постоянный счёт не уменьшается и результат победы не создаётся. Если уже началась фиксация победы, сдача недопустима: HTTP `409 victory_finishing` с актуальными `session` и `player`. Если победа уже подтверждена, возвращаются актуальные `finished`/`won` и сдача не отменяет победу.

Пример HTTP `409`, если победа уже фиксируется:

```json
{
  "error": {
    "code": "victory_finishing",
    "message": "Победа ещё сохраняется. Повторите попытку позже.",
    "details": null
  },
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "finishing",
    "finish_reason": null,
    "state_version": 17
  },
  "player": {"state": "finishing", "session_score": 460}
}
```

Пример HTTP `200` после сдачи:

```json
{
  "surrender": {
    "session_id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "result": "surrendered"
  }
}
```

Подтверждение сохраняется в Redis до конца игрового поколения. Повтор с тем же ключом и телом возвращает то же подтверждение, в том числе после создания новой сессии; он не изменяет новую сессию. Клиент сверяет `surrender.session_id` с отображаемой сессией и переходит к статистике только для соответствующей сессии. При смене поколения или потере Redis подтверждение может исчезнуть: `404` не доказывает, что сессия была сдана. При неопределённости клиент заново запрашивает текущее состояние; недоступность Redis не считается отсутствием сессии.

### `GET /game/sync/`

Периодически возвращает актуальную персональную проекцию игры и открытия на общих участках. Интервал polling задаётся параметром `FRONTEND_SYNC_INTERVAL` и может передаваться фронтенду в контексте шаблона. Клиент может передать `after_version`; в этом контракте сервер возвращает полный snapshot, в том числе если изменений нет.

Клиент выполняет polling в состояниях `playing` и `finishing`. В `finishing` запрос позволяет узнать об успешной фиксации и возвращении `won`; после получения подтверждённого `won` polling этой сессии прекращается. При перезагрузке страницы состояние фиксации восстанавливается и polling возобновляется. `/sync/` не сообщает подтверждённую победу до фиксации результата в PostgreSQL.

Пример query: `GET /game/sync/?session_id=...&after_version=15`

Ответ содержит `session.id` — идентификатор сессии, к которому относится snapshot, а также:

- актуальные `session.status`, `session.finish_reason`, `session.state_version`;
- `player.state`, `player.session_score`, назначенные города и выбранные участки;
- публичные размещения кроссворда игрока;
- для уже отгаданных слов — открытое написание и флаг первого угадавшего; для неотгаданных — только маску/длину и описание.

Пример HTTP `200` в состоянии `playing`:

```json
{
  "session": {
    "id": "09f3284e-cabb-4f4e-b22a-4b2852a9fa10",
    "status": "active",
    "finish_reason": null,
    "state_version": 16
  },
  "player": {
    "state": "playing",
    "session_score": 0,
    "source_city_id": 1,
    "target_city_id": 2,
    "route_ids": [1]
  },
  "crossword": [
    {
      "placement_id": "9ab21bc4-3c72-4317-a442-ecdc95fa605b",
      "route_id": 1,
      "offset_px": 0,
      "letter_count": 6,
      "definition": "Описание слова без его отгадки.",
      "is_guessed": true,
      "guessed_by_me": false,
      "hint_types_used": [],
      "hints": [],
      "word_text": "ПРИМЕР"
    },
```

Sync не начисляет очки и не меняет владельца угаданного слова. После подтверждения победы он возвращает `finished`/`won` и снимок разгаданного кроссворда; статус может стать победным из-за отгадки другого игрока. При ошибке фиксации клиент продолжает видеть `finishing` либо получает явную временную ошибку, а не неподтверждённую победу.

При переходе к `won` интерфейс показывает экран победы и запускает анимацию на условиях раздела 2. Бэкенд не ждёт её завершения. После перезагрузки экран и кроссворд восстанавливаются, пока сохранён снимок.

Чтобы сообщить участнику о победе, бэкенд сохраняет его неактивную сессию со статусом `finished` и снимком до следующего присоединения или общего перезапуска, пока Redis не потерян.

Снимок победы возвращают только `/game/sync/` и `/game/routes/`. Остальные endpoints могут вернуть терминальные `session` и `player`, после чего клиент получает снимок одним из этих двух запросов.

Фронтенд перед применением ответа `/game/sync/` сравнивает его `session.id` с отображаемой сессией. Если идентификаторы не совпадают, ответ игнорируется целиком: он не меняет состояние, кроссворд, счёт или версию. `session.state_version` сравнивается только между ответами одной сессии. Это правило распространяется и на другие ответы игровых запросов.

## 5. Серверные инварианты

1. Пока общий участок используется хотя бы одной активной сессией, для его слова существует одно общее состояние: первое правильное угадывание фиксируется один раз; все участники видят открытие и считают слово пройденным.
2. `placement_id` доступен только участнику, чья проекция содержит слово; идентификатор не даёт прочитать отгадку.
3. Только победа создаёт `GameResult` и изменяет постоянный `users.score`. Завершение сессии без победы (Сдался) не создаёт строку результата.
4. У пользователя не более одной активной сессии, включая находящуюся в фиксации. Одна отгадка может привести к нескольким независимым победам; пара городов и ссылки на участки освобождаются для каждой завершённой сессии.
5. Ни Redis Lua, ни локальная блокировка не делают общую транзакцию с PostgreSQL. До подтверждения результата и сохранения снимка не публикуется `won`; подтверждённый результат не начисляется повторно.

## 6. Восстановление страницы и срок результата

После авторизации backend восстанавливает состояние по идентификатору пользователя из JWT:

- нет активной сессии и сохранённой победы — `watching_stats`;
- города назначены, путь не подтверждён — `selecting_route`;
- путь подтверждён — `playing` с публичной проекцией кроссворда;
- победа фиксируется — `finishing`, без показа подтверждённой победы;
- победа подтверждена — `finished`/`won` со снимком разгаданного кроссворда и возможностью присоединиться к новой игре.

Закрытие страницы не завершает сессию; при истечении JWT сначала требуется повторная авторизация. Снимок победы хранится до новой игры или общего перезапуска; при потере Redis временное состояние тоже может быть утрачено. Уже подтверждённые в PostgreSQL победа и постоянные очки сохраняются. Недоступность Redis возвращается как ошибка сервиса, а не как `watching_stats`.

## 7. Что намеренно не входит

- WebSocket/SSE; синхронизация выполняется polling через `/game/sync/`.
- Публичный доступ к ответам, email или другим приватным данным.
- Персистентные записи каждого действия или состояния активной игры в PostgreSQL.

## 8. История вопросов перед согласованием

Ниже сохранены исходные вопросы и ответы. Решения, уточнённые в последующем обсуждении, зафиксированы в разделах 2–6; в частности, ключ присоединения уникален для каждого намерения, а анимация может запускаться после `finishing` без перезагрузки.

1. **Повтор присоединения.** Предлагается передавать уникальный `Idempotency-Key` для каждого намеренного нажатия «Присоединиться к игре». В течение срока хранения ключа повтор с тем же ключом относится к первоначальной операции и не создаёт новую сессию, даже если она уже завершилась; новое нажатие использует новый ключ. Ключ связывается с пользователем, операцией и игровым поколением. Нужно определить формат и срок хранения ключей, ответ после истечения срока и поведение нескольких вкладок. После общего сброса Redis гарантия распознавания прежнего ключа ограничена сроком жизни игрового поколения.
- Отличная мысль! В запросе присоединения к игре передаем `Idempotency-Key` (конкатенация строк имени пользователя и игрового поколения) в заголовке, чтобы сервер мог распознать повторные попытки и корректно обработать их без создания новой сессии. Сервер должен хранить ключи в Redis на время жизни игрового поколения и использовать их для идентификации повторных запросов.
2. **Сдача и потерянный ответ.** Предлагается отдельный `POST /game/surrender/` с `session_id` и ключом операции. Требуется выбрать, хранить ли кратковременное подтверждение сдачи в Redis для повтора и как долго; без него невозможно отличить успешно обработанную сдачу от потери состояния. После полного перезапуска Redis такая гарантия может исчезнуть.
- Да, добавить отдельный запрос `POST /game/surrender/` с `session_id` и `Idempotency-Key`, хранить кратковременное подтверждение сдачи в Redis для возможности повторного запроса доследующего подключения к игре или в течение времени жизни игрового поколения.
3. **Повтор анимации.** Экран победы и разгаданный кроссворд восстанавливаются обязательно. Предложение из черновика — запускать анимацию лишь при переходе из `playing` к `won`, не повторяя её после обновления. Следует отдельно определить случай восстановления в `finishing`, когда победа подтверждается уже после перезагрузки.
- Когда победа подтверждается после перезагрузки и фронтенд получает состояние `finishing`, анимация не повторяется; она запускается только при переходе из `playing` к `won`. 
4. **Автоматический путь и уже разгаданный маршрут.** Следует решить, должен ли `/game/route/auto/` исключать полностью разгаданные варианты или допустимо показать найденный путь и отклонить его при подтверждении. Для отклонения предлагается отдельный стабильный `409`-код, отличный от `route_not_connected`.
- Автоматический подбор маршрута должен исключать полностью разгаданные варианты и не предлагать их для выбора. 
5. **Недостаточно очков.** Предлагается отдельный стабильный код ошибки для новой подсказки без достаточного баланса и локализованное сообщение. Требуется согласовать HTTP-код и форму ответа; бесплатный повтор полученной подсказки не зависит от баланса.
- HTTP-код 403 мне кажется вполне согласущимся с ситуацией, когда у пользователя недостаточно очков для новой подсказки. С ответом "Для получения подсказки недостаточно очков" на русском языке, и соответствующим ему сообщением на английском языке "Not enough points to get a hint".
6. **Геометрия слов.** Необходимо определить, как сопоставляются `position_index`, промежуток между словами в пикселях и вместимость в ячейках: требование «не больше одной ячейки» само по себе не устанавливает физическую ширину ячейки. Это не должно менять уже опубликованные общие участки.
- Физическая ширина ячейки равна 26 пикселям. Минимальный промежуток между словами в пикселях - 5 пикселей. 
Длину максимального промежутка мы не устанавливаем жестко - промежуток варьируется в зависимости от контекста и доступного пространства. Ограничителем служит пространство на участке, не занятое ячейками со словами. Первоначальная цель - заполнить участок пути словами так, чтобы осталолось общего незаполненного пространства размером не более 2-х ячеек для участка общим размером до 31 единиц из поля `length_in_letters` и не более 3-х ячеек для участка большего размера. Если, согласно изложенному ранее алгоритму, уменьшающему количество выводимых слов из 2-х букв, не удается запонить участки словами длиной больше 2-х букв, допускается оставить большее свободное пространство, при этом оставшееся пространство распределяется равномерно между словами. Если утверждения этого пункта противоречат каким-либо более ранним правилам - заменить эти более ранние правила данным.
Длина общего участка одинакова для каждого из игроков.  
7. **Полные формы ответов.** До реализации согласовать обязательные поля и примеры для `/sync/`, `finishing`, подсказки, сдачи и ошибок, включая локализованные сообщения, `session.state_version` и обработку запоздавших ответов. Определить, в каких ответах помимо `/sync/` и `/routes/` нужен снимок победы, а где достаточно терминального состояния с последующим запросом снимка.
- Ни в каких больше запросах `снимок победы` не нужен.
- Обязательные поля и примеры для `/sync/`, `finishing`, подсказки, сдачи и ошибок, включая локализованные сообщения, `session.state_version` и обработку запоздавших ответов опишите самостоятельно. Как говорилось ранее, конкретные сообщения будут браться из локализованных ресурсов (json-файлов, в том числе, с локализованными сообщениями для ru и en из каталога locales) и могут корректироваться позже. Опишите их сейчас самостоятельно.
